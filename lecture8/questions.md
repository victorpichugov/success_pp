# Лекция 8. Наследование и полиморфизм — вопросы для практики

> Составлено по `final_readme.md`. Формулируй ответ сам, затем сверяйся с `<details>`.
> Вопросы с «что произойдёт»: сначала угадай (скомпилируется? упадёт? утечка?), потом открывай.

---

## Размер объекта при смешанном виртуальном наследовании

### 1. Иерархия: `B : вирт A, невирт C`; `C : вирт A`; `D : B, C` (оба невиртуально). Сколько экземпляров `A` и `C` в объекте `D`?

<details><summary>Ответ</summary>

- `A` — **один**: достижима двумя путями, но **оба виртуальные** → объединяются.
- `C` — **два**: достижима двумя путями, **оба невиртуальные** → своя копия в `B` и своя в `D`.

Плюс «хвосты»: свои части `D` и `B`, и vptr (указатель на виртуальную базу), за который
«платит» каждый класс с виртуальным наследованием.

</details>

### 2. Сформулируй общее правило: сколько экземпляров базы создаётся при разных путях наследования?

<details><summary>Ответ</summary>

**Все виртуальные** пути к базе объединяются в **один** экземпляр; **все невиртуальные** создают
**свою копию** на каждый путь. Смешанное (часть виртуальных, часть невиртуальных) — экземпляр(ы)
общий(ие) + копии по невиртуальным.

</details>

## Приведение типов: срезка, ссылки, касты

### 3. `Base b; Derived d; b = d;` — что происходит и почему это плохо?

<details><summary>Ответ</summary>

**Срезка (slicing)**: присваивается только часть `d`, относящаяся к `Base` — создаётся копия
базовой части, производная **теряется**. Не ошибка компиляции, но почти всегда признак ошибки
в замысле.

</details>

### 4. `Base& b1 = d;` — что доступно через `b1`? Есть ли здесь UB?

<details><summary>Ответ</summary>

Видна **только** базовая часть: `b1.f();` (f из Base), `b1.a;` — OK, `b1.b;` — **ошибка компиляции**.
UB здесь нет — ссылки/указатели на родителя «безопасная сторона»: просто сужение видимости
(аналог `const int& y = x;` — ссылка сужает доступ).

</details>

### 5. В чём разница между `static_cast` и тем, что он **не** проверяет?

<details><summary>Ответ</summary>

`static_cast` проверяет, что по **иерархии** такое преобразование разрешено, но **не проверяет,
чем объект является на самом деле**. Поэтому:

```cpp
Base b;                        // настоящий Base, не Derived
static_cast<Derived&>(b).f();  // скомпилируется, но это UB
```

> «верю на слово, проверяю только иерархию»

</details>

### 6. Если наследование **приватное** — можно ли `static_cast` вниз до потомка? А чем поможет `reinterpret_cast`?

<details><summary>Ответ</summary>

`static_cast` в сторону потомка **запрещён** — наружу не выносится сам факт «`d` — частный случай
`Base`». `reinterpret_cast` — «жесткий инструмент кастовки, **против лома нет приёма**»: несмотря
на приватное наследование, позволяет добраться до полей.

</details>

### 7. Сравни `static_cast` и `reinterpret_cast`: что каждый проверяет?

<details><summary>Ответ</summary>

| | `static_cast` | `reinterpret_cast` |
|---|---|---|
| Проверяет иерархию | да | **нет** |
| Проверяет доступность | да | **нет** |
| Проверяет реальный тип объекта | нет | **нет** |
| Цена ошибки | UB, если «перв» | UB, если «перв» |

</details>

### 8. В ромбе (два пути к `A`) почему `static_cast<A&>(d)` — ошибка, а `reinterpret_cast` «получится»?

<details><summary>Ответ</summary>

`static_cast<A&>(d)` — **ошибка компиляции**: неоднозначно, какой из двух экземпляров `A`.
`reinterpret_cast` (или ручное смещение) работает «в слепую», без анализа иерархии, — компилятор
ему не возражает (но это всё та же «слепая» операция — на свой страх и риск).

</details>

## `dynamic_cast`

### 9. Когда принимает решение `static_cast`, а когда — `dynamic_cast`?

<details><summary>Ответ</summary>

`static_cast` — на этапе **компиляции**. `dynamic_cast` — на этапе **выполнения** (runtime),
после компиляции: проверяет, чем объект является **на самом деле**.

</details>

### 10. Что делает `dynamic_cast` при неудаче для ссылок и для указателей?

<details><summary>Ответ</summary>

- Для **ссылок** — бросает `std::bad_cast` (ссылка не может быть «пустой»);
- Для **указателей** — возвращает `nullptr`, поэтому обычно пишут:

```cpp
if (auto p = dynamic_cast<Derived*>(b1)) {
    p->f();
}
```

</details>

### 11. `A a; C c; B& b = c;` (A ← B ← C). Что `static_cast` скажет про тип `c`? А `dynamic_cast`?

<details><summary>Ответ</summary>

`static_cast` **не проверяет тип** того, что кастуешь — только, что ты имеешь **право** кастовать
по иерархии (иерархически `C → B` разрешено). `dynamic_cast` проверит, чем объект является
на самом деле, и корректно кастует или «сдаётся» (bad_cast / nullptr).

</details>

## Виртуальные функции и полиморфизм

### 12. Без `virtual`: `Derived d; Base& b = d; b.f();` — чей `f` вызовется? Почему?

<details><summary>Ответ</summary>

`Base::f()`. Тип выражения `b` — `Base&`, значит, вызывается версия из типа **ссылки/указателя**
(статическая связка). Факт, что за ссылкой «сидит» `Derived`, игнорируется.

</details>

### 13. Что такое полиморфизм? Приведи бытовую аналогию из лекции.

<details><summary>Ответ</summary>

**Одна и та же функция, применённая к разным сущностям, даёт разный результат.**
Аналогия: «сварить гречку / макароны / рис» — глагол «сварить» в каждом случае означает **разное**
действие: один вызов, разная реализация в зависимости от объекта.

</details>

### 14. Как `virtual` меняет поведение из вопроса 12?

<details><summary>Ответ</summary>

```cpp
struct Base { virtual void f(); };
struct Derived : Base { void f(); };   // virtual «унаследовывается»
Derived d; Base& b = d;
b.f();   // вызовется f из Derived
```

При вызове виртуальной функции рантайм проверяет, **каким является на самом деле** объект,
и вызывает **правильную** версию (динамическая связка).

</details>

### 15. Нужно ли писать `virtual` повторно в производном классе?

<details><summary>Ответ</summary>

Нет — `virtual` **унаследовывается**: если `Base::f` виртуальный, то `Derived::f` с той же
сигнатурой автоматически виртуальный, даже без ключевика.

</details>

## Виртуальный деструктор

### 16. `Derived* d = new Derived(); Base* b = d; delete b;` — скомпилируется? упадёт? утечка?

<details><summary>Ответ</summary>

**Скомпилируется, упасть не упадёт, но будет утечка памяти.** `delete b` смотрит в деструктор
типа `b` (`Base`), видит **невиртуальный** — и удаляет объект «будто это `Base`»: деструктор
`Derived` **никогда не вызывается**, память производной части не освобождается.

</details>

### 17. Практический прецедент из лекции: как именно утечка проявлялась в решении с геометрией?

<details><summary>Ответ</summary>

Задание на иерархию `Rectangle`, `Parallelogram`, `Rhombus`, `Square`; конструкция
`Derived* d = new Derived(); Base* b = d; delete b;` прогонялась **100 000 раз** — из-за утечки
решение падало по **memory limit**. Чинилось одной строкой:

```cpp
struct Base {
    virtual ~Base() {}   // C++11: virtual ~Base() = default;
};
```

</details>

### 18. Сформулируй правило: когда базовому классу **обязан** быть виртуальный деструктор?

<details><summary>Ответ</summary>

Если к классу собираются обращаться **через указатель/ссылку на базовый класс** (включая `delete`),
у базового класса **должен быть виртуальный деструктор**.

</details>

## vtable (вопрос для собеседований)

### 19. Опиши устройство vtable/vptr и как именно выполняется `b.f()`, если `f` виртуальная.

<details><summary>Ответ</summary>

- У каждого объекта с виртуальными функциями есть **vptr** — указатель на **vtable**;
- **vtable** — таблица указателей на функции, **одна на каждый класс** (не на объект);
- Виртуальный вызов: взять vptr из объекта → по нему vtable → из vtable нужный слот → вызвать;
- Поэтому `b.f()` «знает», что объект реально `Derived`: vptr указывает на vtable **того класса,
  которым объект является на самом деле**.

</details>

### 20. Какова цена полиморфизма в памяти и в скорости?

<details><summary>Ответ</summary>

vptr добавляет **8 байт** (на 64-битной) к размеру каждого полиморфного объекта; виртуальный
вызов — **несколько обращений к памяти** вместо прямого (статического) вызова.

</details>

## Абстрактные классы, `override`, `final`, `typeid`

### 21. Что такое чисто виртуальная функция? Что она запрещает?

<details><summary>Ответ</summary>

`virtual double area() const = 0;` — только название, реализации нет. Класс с такими функциями —
**абстрактный**: **запрещает создавать объекты** своего типа. Все наследники **обязаны**
переопределить `area`, иначе наследник сам остаётся абстрактным.

</details>

### 22. Чем отличается «полиморфный» класс от «абстрактного»?

<details><summary>Ответ</summary>

- с **виртуальными** функциями — **полиморфный**;
- с **чисто виртуальными** функциями — **абстрактный**.

Термины не смешивать.

</details>

### 23. В `Shape` объявлено `virtual double area() = 0;` (без `const`), а в `Rectangle` — `double area() const override;`. Что случилось?

<details><summary>Ответ</summary>

`const` — **часть сигнатуры**. Метод в `Rectangle` **не переопределяет** чисто виртуальную функцию,
а является **своей собственной перегрузкой**. Класс остаётся абстрактным — и никто не подскажет
почему. От таких ситуаций застраховывает `override`.

</details>

### 24. Что делает `override` и где его писать?

<details><summary>Ответ</summary>

После сигнатуры метода: «я переопределяю метод предка — проверь меня». Если сигнатура не совпадает
(забыли `const`, поменяли аргументы) — **ошибка компиляции** с понятным сообщением, а не тихая
«перегрузка рядом».

</details>

### 25. Что делает `final`? В каких местах его можно поставить?

<details><summary>Ответ</summary>

- У **класса** — запрещает от него наследоваться: `class Circle final : public Shape {};`.
- У **конкретного виртуального метода** — запрещает переопределить именно его в потомках.

</details>

### 26. «Если объект такого типа — сделай это, если другого — то». Что предложит «тупой» способ? Почему он плох?

<details><summary>Ответ</summary>

«Тупой» способ — `typeid`:

```cpp
if (typeid(x) == typeid(Square)) { ... }
```

Проверяется в рантайме, и **очень долго** — `typeid` сравнивает полные имена типов (строки).
Работает, но считается неграмотным подходом.

</details>

### 27. Каков «грамотный» способ динамического определения типа? На каком этапе он работает?

<details><summary>Ответ</summary>

**Шаблоны** (SFINAE, `if constexpr`, специализации `template<>`) — решают задачу на этапе
**компиляции**, без сравнения типов в рантайме.

</details>

### 28. Итоговый вопрос: `delete base_ptr` по указателю на абстрактный `Shape`. Что должно быть в `Shape`, чтобы не было утечки?

<details><summary>Ответ</summary>

**Виртуальный деструктор**: `virtual ~Shape() {}` (или `= default`). Без него деструктор
производной части не вызывается → утечка на каждом `delete`.

</details>
