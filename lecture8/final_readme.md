## 1. Разбор: размер объекта при смешанном виртуальном наследовании

Вопрос-разминка со смешанной иерархией (вирт = виртуальное наследование):

```
                A
              ^   ^
              |   |
           (вирт) (вирт)
              |   |
D ------------ B -+-> C
 (невирт)      (невирт)
```

- `B` наследует `A` **виртуально** и `C` **невиртуально**;
- `C` наследует `A` **виртуально**;
- `D` наследует `B` и `C`, оба — **невиртуально**.

**Вопрос:** сколько памяти занимает объект типа `D`?

Разбор:

- `A` достижима двумя путями, но **оба виртуальные** → в памяти `D` **один** экземпляр `A` (общий).
- `C` достижима двумя путями, **оба невиртуальные** → **два** экземпляра `C` (своя копия в `B` и своя в `D`).
- Плюс «хвосты»: собственная часть `D`, собственная часть `B`, и указатель на виртуальную базу (vptr), за который «платит» каждый класс с виртуальным наследованием.

> Правило, повторённое из 7-й лекции: **все виртуальные** пути к базе объединяются в **один** экземпляр; **все невиртуальные** создают **свою копию**.

## 2. Приведение типов между предком и потомком

Пусть есть:

```cpp
struct Base {
    int a;
    void f();
};

struct Derived : Base {
    int b;
    void f();
};

Base b;
Derived d;
```

(Считаем, что всё публичное.)

### 2а. Срезка (slicing)

```cpp
b = d;   // компилируется
```

Присваивается **только та часть `d`, которая относится к `Base`** — создаётся копия базовой части, производная часть **теряется**. Не ошибка, но почти всегда признак ошибки в замысле.

```
|   |
-----
|   ||   |
----------
```

### 2б. Ссылка/указатель на родителя

```cpp
Base& b1 = d;   // ссылка на базовую часть d — OK
```

Через `b1` видна **только** часть `d`, относящаяся к `Base`:

```cpp
b1.f();  // вызовется f из Base
b1.a;    // OK
b1.b;    // ОШИБКА КОМПИЛЯЦИИ
```

Аналогия: `const int& y = x;` — ссылка «сужает» доступ к объекту.

С указателями то же самое:

```cpp
Base* b1 = &d;

b1->f();  // f из Base
b1->a;    // OK
b1->b;    // ОШИБКА КОМПИЛЯЦИИ
```

> Ссылки и указатели на родителя — «безопасная сторона»: никакого UB, просто сужение видимости.

### 2в. Каст вниз: `static_cast`

Как добраться до производной части?

```cpp
static_cast<Derived&>(b1).f();   // работает — b1 действительно указывает на Derived
```

Обратное направление тоже законно по иерархии. С указателями аналогично (после каста — `->`):

```cpp
static_cast<Derived*>(b1)->f();
```

**Но** `static_cast` **не проверяет, чем объект является на самом деле** — он только проверяет, что по иерархии такое преобразование **разрешено**. Поэтому:

```cpp
static_cast<Derived&>(b).f();   // b — настоящий Base, НЕ Derived
```

скомпилируется, но это **undefined behavior**.

> `static_cast` — «верю на слово, проверяю только иерархию».

### 2г. Приватное наследование и `reinterpret_cast`

Если наследование **приватное**, то наружу не выносится сам факт «`d` — частный случай `Base`», и `static_cast` в сторону потомка **запрещён**.

Но хочется — можно:

```cpp
// до reinterpret_cast: d.a — нельзя
// после reinterpret_cast — можно
```

`reinterpret_cast` — «жесткий инструмент кастовки, **против лома нет приёма**»: несмотря на приватное наследование, он позволяет добраться до полей.

| | `static_cast` | `reinterpret_cast` |
|---|---|---|
| Проверяет иерархию | да | **нет** |
| Проверяет доступность | да | **нет** |
| Проверяет реальный тип объекта | нет | **нет** |
| Цена ошибки | UB, если «перв» | UB, если «перв» |

### 2д. Неоднозначность в ромбе

Если `D` достижим к `A` **двумя путями**, то:

```cpp
static_cast<A&>(d);   // ОШИБКА КОМПИЛЯЦИИ — неоднозначно: какой A?
```

При этом `reinterpret_cast` (или ручное смещение указателей) **получится** — они работают «в слепую», без анализа иерархии, и поэтому компилятор им не возражает.

## 3. `dynamic_cast`

Пусть цепочка наследования (всё публично):

```
     A
     ^
     |
     B
     ^
     |
     C
```

```cpp
A a;
C c;

B& b = c;   // c на самом деле — C, но типом — B
```

Напоминание: `static_cast` **не проверяет тип** того, что вы кастуете — он проверяет только, что вы **имеете право** кастовать по иерархии.

**`dynamic_cast` проверяет, чем объект является на самом деле**, и в зависимости от этого:

- при возможности — корректно кастует;
- при невозможности — «сдаётся».

Ключевое отличие по моменту проверки:

- `static_cast` — решение принимается **на этапе компиляции**;
- `dynamic_cast` — проверка **на этапе выполнения** (runtime), после компиляции.

Разбор: для ссылок `dynamic_cast` при неудаче бросает `std::bad_cast`, для указателей — возвращает `nullptr`, и его обычно пишут в форме:

```cpp
if (auto p = dynamic_cast<Derived*>(b1)) {
    p->f();
}
```

> `static_cast` — быстро и «верю на слово». `dynamic_cast` — медленнее и «проверяю».

## 4. Виртуальные функции

Очень важно для собеседований. Это одно из проявлений полиморфизма.

### 4а. Проблема: без `virtual` вызывается версия из типа **ссылки/указателя**

```cpp
struct Base {
    void f();
};

struct Derived : Base {
    void f();
};

Derived d;
Base& b = d;

b.f();   // вызовется f, которая в Base
```

Тип выражения `b` — `Base&`, значит, вызывается `Base::f()`. Факт, что за ссылкой «сидит» `Derived`, **игнорируется**.

Практический пример: есть набор указателей/ссылок на объекты, пробегаем по ним и для каждого что-то спрашиваем, например, **площадь**. Но фигуры бывают разные, и логично, чтобы объект вёл себя не «как базовый», а **так, каким он является на самом деле**.

### 4б. Полиморфизм

> **Полиморфизм** — одна и та же функция, применённая к разным сущностям, даёт разный результат.

Бытовая аналогия: «сварить гречку», «сварить макароны», «сварить рис». Глагол «сварить» в каждом случае означает **разное** действие — один и тот же вызов, разная реализация в зависимости от объекта.

### 4в. Решение: `virtual`

```cpp
struct Base {
    virtual void f();
};

struct Derived : Base {
    void f();   // virtual «унаследовывается»
};

Derived d;
Base& b = d;

b.f();   // вызовется f, которая в Derived
```

**Виртуальная функция** — функция, при вызове которой компилятор/рантайм **проверяет, каким является на самом деле** объект, у которого её вызывают, и вызывает **правильную** версию.

Именно `virtual` позволяет осуществить полиморфизм.

## 5. Виртуальный деструктор

### 5а. Как устроена утечка

```cpp
Derived* d = new Derived();
Base* b = d;

delete b;
```

**Вопрос:** скомпилируется ли код? Упадёт? Если не упадёт — всё ли будет хорошо?

Ответ: **скомпилируется, упасть не упадёт, но будет утечка памяти.**

Что происходит: `delete b` — компилятор смотрит в деструктор **типа `b`** (`Base`), видит, что он **невиртуальный**, и удаляет объект **так, будто это `Base`** — деструктор `Derived` **никогда не вызывается**. Память, занятая «производной» частью, не освобождается.

### 5б. Практический прецедент

У прошлых потоков было задание на иерархию геометрических классов `Rectangle`, `Parallelogram`, `Rhombus`, `Square`. В решении была конструкция:

```cpp
Derived* d = new Derived();
Base* b = d;
delete b;
```

и она прогонялась **100 000 раз** — из-за утечки решение падало по **memory limit**.

Чинилось одной строкой:

```cpp
struct Base {
    virtual ~Base() {}   // или в C++11: virtual ~Base() = default;
};
```

### 5в. Правило

> Если вы пишете класс и собираетесь обращаться к нему **через указатель/ссылку на базовый класс** (включая `delete`), у базового класса **должен быть виртуальный деструктор**.

## 6. Как в памяти хранятся классы с виртуальными функциями

Вопрос, открытый на лекции и помеченный как **вопрос для собеседований**: *таблица виртуальных функций (vtable).*

Разбор (доклад на следующий раз должен быть готов):

- у каждого объекта с виртуальными функциями в памяти есть **vptr** — указатель на **vtable**;
- **vtable** — таблица указателей на функции, **одна на каждый класс** (не на каждый объект);
- виртуальный вызов `b.f()` — это: взять vptr из объекта, по нему — vtable, из vtable — нужный слот, вызвать его;
- поэтому `b.f()` в 4в «знает», что это `Derived`: vptr у объекта указывает на vtable **того класса, которым объект реально является**.

Стоимость: vptr добавляет **8 байт** (на 64-битной) к размеру каждого полиморфного объекта, виртуальный вызов — **несколько обращений к памяти** вместо прямого.

## 7. Абстрактные классы

Пусть есть геометрические фигуры `Rectangle`, `Parallelogram`, `Rhombus`, `Square`; у каждой есть метод площади, и я хочу создать **массив фигур**, не уточняя, какие именно фигуры.

Решение — **чисто виртуальная функция**:

```cpp
class Shape {
public:
    virtual double area() const = 0;   // не подразумевает реализации
    virtual ~Shape() {}                // и виртуальный деструктор!
};
```

Функция вида `virtual double area() const = 0;` — **чисто виртуальная (pure virtual)**: только название, реализации нет, и **объекты такого типа создать нельзя**.

> Класс, в котором есть чисто виртуальные функции, называется **абстрактным**. Абстрактные классы **запрещают создавать объекты** своего типа.

Смешивать термины нельзя:

- класс с **виртуальными** функциями — **полиморфный**;
- класс с **чисто виртуальными** функциями — **абстрактный**.

`area` **обязаны** переопределить все, кто наследует `Shape`, — иначе наследник сам остаётся абстрактным, и его тоже нельзя инстанцировать:

```cpp
class Circle : public Shape {
    // забыл area()
};

// Circle c;   // ОШИБКА — Circle всё ещё абстрактный
```

### 7а. Каверза: забыл `const` перед `= 0`

```cpp
class Shape {
public:
    virtual double area() = 0;   // без const
};

class Rectangle : public Shape {
    double area() const override;   // const — другой сигнатурой
};
```

`const` — **часть сигнатуры**. Записав `area() = 0` без `const`, вы **не объявили тот метод, который ожидает наследник**, а написали **свой собственный** метод, который живёт по общим правилам **перегрузки** и чисто виртуальную функцию **не переопределяет**. Класс остаётся абстрактным — и никто не подскажет почему.

От таких ситуаций C++ застрахован словом **`override`** (ниже).

## 8. `override` и `final`

### 8а. `override`

Писать **после сигнатуры** метода:

```cpp
class Rectangle : public Shape {
    double area() const override = 0;   // переопределяю метод предка — проверь меня
};
```

Если сигнатура не совпадает с методом предка (забыли `const`, поменяли аргументы) — **ошибка компиляции** с понятным сообщением, а не тихая «перегрузка рядом».

> `override` — «я переопределяю метод предка», и компилятор **проверяет** это.

### 8б. `final`

```cpp
class Circle final : public Shape {
    double area() const override;
};

// class Bad : public Circle {};   // ОШИБКА — Circle нельзя наследовать
```

`final` **запрещает** от класса наследоваться (также можно поставить и на конкретный виртуальный метод — запретить именно его переопределение в потомках).

## 9. Динамическое определение типа

Задача: «если объект такого-то типа — сделай это, если другого — то».

### 9а. Простой (тупой) способ: `typeid`

```cpp
if (typeid(x) == typeid(Square)) {
    // ...
}
```

Проверяется **на этапе исполнения**, и это **очень долго** — `typeid` сравнивает полные имена типов строк. Работает, но считается «не грамотным» подходом.

### 9б. Грамотный способ: шаблоны

Лекция обрывается на этом пункте — шаблоны позволяют решить задачу **на этапе компиляции** (SFINAE, `if constexpr`, `template<>`-специализации), не сравнивая типы в рантайме.

> Задача после лекции: реализовать «если тип такой-то — сделай это» тремя способами: `dynamic_cast`, `typeid`, шаблоны — и сравнить.

## Короткая шпаргалка

| Тема | Главное |
|---|---|
| **Виртуальная база** | Все виртуальные пути → **один** экземпляр; невиртуальные → **своя копия** на каждый путь |
| **Slicing** | `b = d;` — копируется только базовая часть, производная **теряется** |
| **`Base& b = d`** | Видна только базовая часть: `b.b` — ошибка компиляции |
| **`static_cast` вниз** | Проверяет **иерархию**, не проверяет **реальный тип** → «первёшь» — UB |
| **`reinterpret_cast`** | «Против лома нет приёма»: ничего не проверяет, ломает даже приватное наследование |
| **`dynamic_cast`** | Проверяет **реальный тип в рантайме**; ссылки → `bad_cast`, указатели → `nullptr` |
| **Невиртуальная `f`** | Вызывается версия из **типа ссылки/указателя** (статическая связка) |
| **`virtual void f()`** | Вызывается версия из **реального типа** объекта (динамическая связка) |
| **Полиморфизм** | Одна функция → разные результаты в зависимости от объекта |
| **`delete base_ptr`** | Без `virtual ~Base()` — **утечка**: деструктор производного класса не вызывается |
| **Правило** | Класс, через который «удаляют»/«зовут» от базового указателя → **виртуальный деструктор** |
| **vtable** | У полиморфного объекта — vptr на таблицу функций класса; виртуальный вызов — через неё |
| **`area() const = 0`** | Чисто виртуальная → класс **абстрактный**, объекты нельзя создавать |
| **Полиморфный vs абстрактный** | С виртуальными — полиморфный; с чисто виртуальными — абстрактный |
| **Забыл `const` в `= 0`** | Получил **перегрузку**, а не переопределение → класс всё ещё абстрактный, тихо |
| **`override`** | После сигнатуры: «я переопределяю предка — проверь» |
| **`final`** | Запрет наследоваться (класс) или переопределять (метод) |
| **`typeid`** | Сравнение типов в рантайме — работает, но **долго** |
| **Шаблоны** | Грамотное «динамическое» определение типа — на этапе **компиляции** |
