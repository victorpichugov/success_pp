Лекция 15 RAII и умные указатели (unique_ptr, shared_ptr, weak_ptr)

зачем вообще лекция: с 6-й лекции висел вопрос «Что такое умный указатель?»,
в 11-й лекции обещали («это умные указатели!!! (smart pointers), их цель решать проблемы
утечки памяти»), в 13-й сформулировали задачу («Проблема подсчета ссылок: нужно хранить
указатель + счетчик»). закрываем всё разом

1) RAII = Resource Acquisition Is Initialization

утечка из 11-й лекции:
struct Ugly {
    int* p;
    Ugly() { p = new int; throw 1; }
    ~Ugly() { delete p; }        // НИКОГДА не вызовется
};
исключение в конструкторе → объект не достроен → деструктор НЕ вызывается → p потеряна

деструкторы баз и полей отработают (построенная часть уничтожается), а «недостроенный»
объект — нет. поэтому delete не может зависеть от «дожил ли код до строки»

идея: привязать освобождение ресурса к ЛЮБОМУ выхода из области видимости.
выход из области → вызовутся деструкторы локальных объектов (stack unwinding).
значит если ресурс в поле объекта, он освобождается гарантированно:
нормальный выход, return, break, throw

Ресурсом владеет объект, деструктор освобождает.

ресурс — это не только память:
файл (fopen/fclose), сокет, мьютекс (lock/unlock), соединение с IP-сетью (пример из 11-й),
дескриптор из SDK, место в пуле, «записал в лог начало/конец»
вопрос на собесе: чем RAII отличается от «попробуй/поймай» — ответ: освобождение по
структурной скобке, а не по потоку управления

сборки мусора в C++ нет (в Java есть) — за ресурсы отвечают деструкторы

каверза: деструктор RAII-обёртки обязан быть noexcept (11-я лекция: бросок из деструктора
при размотке → terminate). внутри try { } catch (...) { }

2) auto_ptr — исторический урок (C++98, удалён в C++17)

auto_ptr<T> a(new T);
auto_ptr<T> b = a;    // КОПИРОВАНИЕ ОБНУЛЯЕТ ИСТОЧНИК (a == nullptr)
«конструктор копирования» с побочным эффектом → объект больше не value-семантики

ловушка: функции вида
std::auto_ptr<T> f(const std::auto_ptr<T>& p) { return p; }   // не компилируется:
                                          // «копирование» требует не-константный источник
vector<auto_ptr<T>> ломается: push_back принимает const&, а копирование требует
non-const источник → «binding reference ... discards qualifiers»

удалён из стандарта в C++17. в gcc 11 остаётся только deprecated-объявление:
'(template<class> class std::auto_ptr' is deprecated: use 'std::unique_ptr' instead

вывод: умный указатель обязан быть ЧЕСТНЫМ: копия либо есть копия, либо её нельзя сделать

3) unique_ptr

unique_ptr<T, D>   // D — deleter, по умолчанию default_delete<T>
нет конструктора копирования → move-only (проверено: unique_ptr<C> b = a; не компилируется)
sizeof == 8 при deleter без состояния; deleter — часть ТИПА

make_unique<T>(args) (C++14) — одна аллокация, исключения-safe, нет ручного new
в C++11 make_unique нет (проверено)

массивы: unique_ptr<T[]> → delete[], operator[] есть, operator-> нет (проверено: не компилируется)
make_unique<T[]>(n) — value-init (обнуление)
shared_ptr<T[]> в C++17 есть, а make_shared<T[]> — НЕТ (static_assert)

deleter:
FILE* → fclose, ручки SDK → CloseHandle/Release, «вернуть в пул»
stateless deleter (struct с operator()) → sizeof остаётся 8
указатель на функцию → sizeof 16
std::function → sizeof 40 (проверено на gcc 11: sizeof == 40)
вопрос на собесе: «уникальный указатель с делетером какого размера?» — зависит от deleter

reset(p) — освобождает старое, принимает новое
release() — ОСВОБОЖДАЕТ ВЛАДЕНИЕ, возвращает сырой указатель, свой обнуляет:
Tracked* raw = p.release();  // теперь delete raw — на мне
«release = забираешь сырой указатель на себя»

фабрика (11-я лекция: «конструктор держать закрытым»):
class C { explicit C(int fd); public: static std::unique_ptr<C> create(int fd) {
    if (fd < 0) throw ...; return std::make_unique... нет, ctor приватный → unique_ptr<C>(new C(fd)); }}
make_shared не пройдёт через приватный конструктор — в этом плюс фабрики

параметр функции unique_ptr<C> p = «Я ЗАБИРАЮ ВЛАДЕНИЕ» (вызывающий обязан std::move)
возврат из функции unique_ptr — единственный способ вернуть полиморфного/некопируемого
(лекция 14 про NRVO/move — плановая)

«Почему frame — shared_ptr, а кэш — unique_ptr?» (вопрос ревьюера из vacancy_tasks):
frame — общие read-only данные, владельцев много → shared_ptr
кэш — ровно один хозяин, он его и создаёт/уничтожает → unique_ptr, копия не нужна

4) shared_ptr

контрольный блок (control block): { strong_count, weak_count, deleter, allocator }
СЧЁТЧИК НЕ ВНУТРИ ОБЪЕКТА (не intrusive!) — поэтому shared_ptr работает с чужими классами
операции со счётчиком АТОМАРНЫ (мьютекс на блок навешивать не надо)

ответ на 13-ю лекцию «как должен выглядеть конструктор копирования?» и «через deepcopy()»:
deepcopy не нужен — копия shared_ptr = КОПИЯ УКАЗАТЕЛЯ + ИНКРЕМЕНТ СЧЁТЧИКА
копия за O(1), объект не копируется

use_count() — число сильных владельцев; unique() — use_count()==1 (в C++20 устарело)
порядок уничтожения: последний владеющий вызывает deleter (запомнен СТАТИЧЕСКИМ типом
в момент взятия владения!), потом деструкторы по цепочке

аллокации (проверено счётчиком через глобальный operator new):
shared_ptr<T>(new T)   → 2 аллокации (объект + блок)
make_shared<T>()       → 1 аллокация (объект и блок одним куском)
ловушка make_shared: память объекта не освободится, пока жив хоть один weak_ptr,
даже когда use_count == 0 и объект уже уничтожен (проверено: expired=1, память занята)
allocate_shared(alloc, args) — «под ключ» из 12-й лекции, свой аллокатор на блок+объект

enable_shared_from_this<T> — CRTP из 10-й лекции (готовый пример)
внутри лежит WEAK указатель на себя
shared_from_this() до помещения во владение — UB (в gcc кидает bad_weak_ptr → terminate)
weak_from_this() (C++17) — безопасный вариант, вернёт пустой weak_ptr

конверсия shared_ptr<Derived> → shared_ptr<Base> — есть (это полиморфизм)
обратный конструктором — нельзя (нужен static_pointer_cast / dynamic_pointer_cast (C++17))

полиморфный delete (8-я лекция, виртуальный деструктор):
shared_ptr<Base>(new Derived) БЕЗ virtual ~Base → ~Derived ВЫЗОВЕТСЯ, утечки нет (проверено + ASan),
потому что делетер записан в блок в момент конструктора и помнит Derived
DELTER «СЪЕДАЕТ» необходимость виртуального деструктора
но unique_ptr<Base>(new Derived) без virtual ~Base → UB (проверено ASan: new-delete-type-mismatch),
уникальный указатель виртуального деструктора НЕ прощает

5) циклы ссылок и weak_ptr

class Node { shared_ptr<Node> next; };
a->next = b; b->next = a;   // use_count: a=2, b=2
область кончилась → счётчики упали до 1 → ноль не достигнут → деструкторы НЕ вызваны → УТЕЧКА
лечится: weak_ptr<Node> (не владеет, счётчик strong не двигает)

weak_ptr: lock() → shared_ptr (или nullptr), expired(), use_count(), weak_count()
у shared_ptr метода weak_count() НЕТ (проверено: нет такого члена)
слабый владелец держит только контрольный блок, не объект
weak_ptr — это НАБЛЮДАТЕЛЬ (observer) и кэш; в map<id, weak_ptr> — идеальная пара

6) правила владения (для собеса)

сырой указатель/ссылка = НАБЛЮДАТЕЛЬ, не владеет, всегда «позаимствовано у кого-то»
никогда shared_ptr<T>(new T) в аргументах функции:
f(shared_ptr<A>(new A), g()) — порядок вычисления аргументов НЕ определён, если g() бросит
после new A → утечка (детерминированный вариант: сырой указатель живёт до shared_ptr — ASan
показывает leak)
правильно: f(std::make_shared<A>(...), g())
передаём по const shared_ptr<T>& (копия = инкремент счётчика, атомарная операция)
const shared_ptr<T> — константен УКАЗАТЕЛЬ (объект менять можно, проверено)
shared_ptr<const T> — константен ОБЪЕКТ (писать нельзя, проверено: не компилируется)
потокобезопасность: счётчик — да (атомарно), САМ ОБЪЕКТ — нет (нужен мьютекс)
std::atomic<std::shared_ptr<T>> — C++20; std::atomic_load/store для shared_ptr (C++11) — устарели

7) руками (домашнее задание)

IntrusivePtr — счётчик ВНУТРИ объекта (базовый RefCounted) → sizeof 8, 0 аллокаций,
но требует править класс + delete по базе без virtual = UB
RefCntPtr — счётчик в отдельном блоке: ctor/copy(инкремент)/move/dtor/swap/* /-> (6-я лекция!)
что ломается: потоки (нужен atomic счётчик), циклы, исключения в конструкторе

8) сводка: unique — один хозяин; shared — несколько; weak — наблюдатель;
сырой указатель — наблюдатель без гарантий; optional — владение без new

вопросы на экзамене

1. Дано:
   auto a = std::make_shared<T>("a");
   { auto b = a; auto c = b; auto e = std::move(c); }
   Чему равны use_count у a, b, c, e внутри блока и у a после блока?
   (проверено: 3, 3, 0, 3; после блока 1)

2. Два объекта с shared_ptr на друг друга в цикле. Сколько ~Node напечатается?
   (проверено: ноль, утечка; починить одной строкой — weak_ptr)

3. auto p = std::make_shared<Big>(); std::weak_ptr<Big> w = p; p.reset();
   Сколько аллокаций, жив ли объект, свободна ли память, что вернёт w.lock()?
   (объект уничтожен, use_count=0, expired=1, память НЕ освобождена из-за make_shared; lock() → nullptr)
