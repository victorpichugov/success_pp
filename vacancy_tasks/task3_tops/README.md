# Task 3. WeightedIntersect — пересечение топов по «лучшей позиции»

## Контекст (что это в команде)

Сравнение двух выдач ранжирования: наша (planner A) и референсная
(planner B / прод). Каждому объекту в каждом топе соответствует
позиция. Нужен список общих объектов, отсортированный по
«насколько хорошо объект ранжируется в ЛУЧШЕЙ из двух выдач»:
ключ = min(pos_a, pos_b), по возрастанию. Тир-брейк — по pos_a
(порядок в топ-а). Это вход для отчёта «насколько наши выдачи
расходятся в топе-N».

Теперь это развитие `practice/top_intersection` (там была «простая»
версия без весов): порядок теперь НЕ порядок top_a — нужен сортирующий
проход.

## Спецификация (НЕ менять, только выполнять)

- Входы: `top_a`, `top_b` — id, **в каждом списке id уникальны**
  (спека взвешенной версии; про валидацию — устный вопрос).
- Выход: `std::vector<int>` — id, встречающиеся в ОБЕИХ списках;
  порядок: по `min(pos_a, pos_b)` по возрастанию; при равенстве —
  по `pos_a` по возрастанию. (pos_a уникален в результате, так что
  порядок тотальный.)
- Сложность: в среднем O(n + m) + O(k log k), k = |пересечение|;
  память O(n + m).

   top_a = {5, 3, 9, 7}, top_b = {3, 5, 9, 8}:
     5 -> min(0,1)=0; 3 -> min(1,0)=0; 9 -> min(2,2)=2
     -> по min: 5 (pos_a 0) и 3 (pos_a 1) — тир, порядок top_a -> 5, 3;
        потом 9. Итог: {5, 3, 9}.
   top_a = {42, 7, 5, 9, 3, 1}, top_b = {9, 5, 1, 8, 2, 6}:
     5 -> min(2,1)=1; 9 -> min(3,0)=0; 1 -> min(5,2)=2
     -> {9, 5, 1}.  <-- вот этот кейс ломает «просто пройтись по top_a»:
        порядок top_a дал бы {5, 9, 1} — НЕВЕРНО.

## ТЗ

`weighted_tops.h`: исправить legacy (двойной цикл O(n*m)).

ДВА подхода — сначала устно ОБА, потом выбираешь один:
(A) хеш-таблица: `unordered_map<int, size_t>` позиций top_b (или
    меньшего списка — подумай, почему), сканирование top_a,
    сборка вектора пар (key, pos_a, id), `std::sort`.
(B) сортировка + два указателя: сортируем копии по id, идём двумя
    указателями, собираем пересечение, потом сортируем по (key, pos_a).
Сравни: время, память, порядок, гарантированность без дегенерации
хеши (worst case `unordered_map` и как застраховать: reserve +
max_load_factor; альтернативы).

## Устные вопросы

1. Почему нельзя «просто пройтись по top_a и отфильтровать»? (ключ —
   min, не pos_a. Кейс-контрпример — в спецификации.)
2. `unordered_map` или `std::map`? Когда каждый выигрывает?
3. `reserve` на map и на result: зачем и сколько?
4. Если id МОГУТ дублироваться в топ-ах (возврат к спецификации
   practice/top_intersection) — что сломается в (A)? Как поправить?
5. k log k — когда доминирует? (k мало / k ~= n.)
6. Bonus: если входы УЖЕ отсортированы по score — какой подход оптимален
   без хеша? (два указателя на исходных.)

## Тесты (минимальный набор, в main.cpp)

Точность (полное сравнение векторов):

- {42,7,5,9,3,1} x {9,5,1,8,2,6} -> {9,5,1}   (критичный кейс)
- {10,1} x {1,10}              -> {10,1}      (тир по min)
- {1,2,3} x {3,2,1}            -> {1,2,3}     (mirroring)
- {1,2} x {3,4}                -> {}
- {} x {1,2}                   -> {}
- {7} x {7}                    -> {7}
- {1,100} x {100,1}            -> {1,100}? ПОДСЧЁТ САМ: 1->min(0,1)=0;
                                 100->min(1,0)=0; тир: pos_a: 1(0) < 100(1) -> {1,100}
