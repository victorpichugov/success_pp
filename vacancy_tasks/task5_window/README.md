# Task 5. MaxConcurrent — максимум машин одновременно на участке

## Контекст (что это в команде)

Анализ загрузки участка дороги (для сценариев симуляции и отладки):
по логам известен набор моментов ВЪЕЗДА и ВЫЕЗДА каждой машины.
Нужно максимальное число машин, находившихся на участке одновременно.
Задача «контестная» (уровень medium), типичная для технических
раундов Яндекса: два отсортированных массива, два указателя.

## Спецификация

- Входы: `enter`, `exit` — `std::vector<long long>`, ОДИНАКОВОЙ длины,
  ОТСОРТИРОВАННЫЕ по неубыванию. (Сопоставление enter[i] <-> exit[i]
  НЕ используется и НЕ гарантировано: алгоритм работает по мультимножествам.)
- Конвенция присутствия: машина на участке в момент t, если
  `enter <= t < exit` (выезд в момент t — уже не на участке).
- Выход: `long long` — максимум по всем моментам t.
- Пустой ввод -> 0.
- Сложность: O(n) время, O(1) доп. память (входы не трогаем).

Ключевая идея (устно, до кода):
максимум достигается СРАЗУ ПОСЛЕ КАКОГО-ТО ВЪЕЗДА (число машин
растёт только на въездах). Поэтому достаточно проверить n моментов
`enter[i]`: сколько машин въехали (`i + 1`) и сколько уже выехали
(`exit[j] <= enter[i]` -> j). Второй указатель только идёт вперёд
(обе последовательности неубывающие) -> суммарно O(n).

## Legacy

`traffic.h`: наивный O(n^2) — для каждого въезда перебор всех машин.
На n = 10^6 — 10^12 операций (часы). Это «красный» перф-тест.

## ТЗ

`traffic.h`: исправить до O(n), O(1) доп. памяти.

## Устные вопросы

1. Почему достаточно проверять моменты `enter[i]`, а не все t?
2. Почему указатель `left` (выезды) не нужно сбрасывать на каждом i?
3. Порядок операций в момент t: выезды раньше въездов или наоборот?
   (У нас конвенция enter <= t < exit — зафиксирована в спеке.
   Что изменится в ответе, если конвенция `enter < t <= exit`?)
4. enter == exit (машину «заезжает и сразу выезжает»): считается
   присутствовавшей? (По конвенции — нет.)
5. Если входы НЕ отсортированы — что сделать и какова сложность?
   (sort обоих: O(n log n); или std::multiset / merge.)
6. Bonus: вернуть НЕ только максимум, но и момент (интервал), когда
   он достигнут. Сколько дополнительных полей и где ловить?
7. long long вместо int: зачем (время — unix-наносекунды, 10^18).

## Тесты (минимальный набор, in main.cpp)

Точность:
- {} x {}                       -> 0
- {1,1,1} x {2,2,2}             -> 3
- {1,2,3} x {2,3,4}             -> 1  (никогда не пересекаются)
- {5} x {5}                     -> 0  (enter == exit: нет присутствия)
- {1,2} x {3,3}                 -> 2
- {1,3,7} x {4,5,8}             -> 2  (машин 1 и 2 на [3,4))
- {0,0,1,1} x {1,2,2,3}         -> ?  (посчитать самому по конвенции)

FUZZ (обязательно): 300 случайных малых случаев (n до 40, времена
0..50), сравнение с «тупым» O(n^2) brute force (перебор моментов
`enter[i]`, подсчёт `enter[j] <= t && exit[j] > t`).

Perf: n = PERF_N (по умолчанию 10^6), enter[i] = 2*i,
exit[i] = 2*i + PERF_N/2 -> ответ PERF_N/2. Бюджет 100 мс.
На legacy не гонять с 10^6 — собери legacy с `-DPERF_N=2000`
(4*10^6 операций — быстро) просто чтобы увидеть, что на малом n
legacy тоже «зелёный» по содержимому, а «красный» только по масштабу.
