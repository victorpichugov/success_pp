# Task 6. ParseLog — парсер лога событий объектов

## Контекст (что это в команде)

Дабаг-дамп / IPC-канал: строки вида

    t=123.45 id=7 x=-1.5 y=2.5 type=car lane=3

описывают события объектов. Формат «полезный», но не строгий:
поля в ЛЮБОМ порядке, могут быть ДОПОЛНИТЕЛЬНЫЕ неизвестные поля
(модули обновляются асинхронно — у новых модулей новые поля),
и в лог попадают повреждённые строки (обрывы пакета, гонки
при записи). Ломать парсер из-за одной битой строки нельзя —
битые строки ПРОСКАКИВАЮТСЯ, и их количество считается
(отдельная метрика для мониторинга).

## Спецификация

Строка = последовательность `key=value`, разделителей — ОДИН
пробел (но допустимы и пустые «швы» — просто игнорируем лишние).

Обязательные поля: `id` (целое, `std::stoll`), `t`, `x`, `y`
(`double`, `std::stod`). Значение должно разбираться ЦЕЛИКОМ
("1.5.5", "7abc", "" — повреждено). Конечность: `std::isfinite`.
Неизвестные ключи (например `type=car`) — ИГНОРИРОВАТЬ.

Вывод:
    struct ObjectEvent { long long id; double t, x, y; };
    struct ParseResult { std::vector<ObjectEvent> events; std::size_t skipped; };
    ParseResult ParseLog(const std::vector<std::string>& lines);

- повреждённая строка — НЕ бросаем исключение наружу, `++skipped`;
- пустая строка — тоже `++skipped`;
- порядок `events` = порядок строк;
- Time O(сумма длин), Space O(кол-во валидных строк).

## Legacy

`log_parser.h`: `sscanf` с ЗАФИКСИРОВАННЫМ порядком `"t=... id=... x=... y=..."`.
Работает только на канонировке; ломается на перестановке, доп. полях,
«хвостах». Тесты ниже — «красный».

## ТЗ (что исправить)

`log_parser.h`: разбор по полям (не по позиции). Идеи реализации —
на выбор: `find('=')` + `find(' ')` по кусочкам, либо `std::istringstream`
+ `>>` (медленнее, но проще; оцени сложность ОБЕИХ устно).

## Устные вопросы

1. Почему `sscanf` с фиксированным форматом — антипаттерн для
   «живого» формата? (порядок, доп. поля, хвосты.)
2. `std::stod("1.5.5")` — что вернёт и сколько `pos`? Как поймать
   «не целиком»? (pos != size.)
3. `std::stoll("")` / `std::stoll("1e3")` / `std::stoll("99999999999999999999")` —
   что произойдёт в каждом? (исключения: invalid_argument /
   out_of_range — и что делать: catch -> skipped.)
4. NaN/Inf в `t=nan`? (std::stod разбирает "nan"! -> isfinite -> skipped.)
5. Почему возвращаем `ParseResult` by value, а не заполняем
   аргументы-ссылки? (RVO, чистый API, move внутри.)

## Тесты (минимальный набор, in main.cpp)

Точность:
- "t=1.5 id=7 x=-2.0 y=3.25"        -> 1 event {7, 1.5, -2, 3.25}
- "id=7 x=-2.0 y=3.25 t=1.5"        -> 1 event (порядок другой)
- "type=car t=1.5 id=7 x=0 y=0"     -> 1 event (доп. поле)
- "t=1e1 id=1 x=0 y=0"              -> 1 event, t = 10
- "t=abc id=1 x=0 y=0"              -> skipped
- "id=1 t=1 x=0 y=0"                -> OK (id целое)
- "id=1.5 t=1 x=0 y=0"              -> skipped (id не целиком)
- "id=1 t=1 x=0 y="                 -> skipped (пустое значение)
- "id=1 t=1 x=0"                    -> skipped (нет y)
- "id=1 t=nan x=0 y=0"              -> skipped (неконечное)
- ""                                -> skipped
- "id=1 t=1 x=0 y=0 lane=3"         -> 1 event (доп. поле в хвосте)
- 3 строки (2 OK + 1 битая)         -> events.size() == 2, skipped == 1

Perf: 100 000 валидных строк (генерация в цикле), бюджет 200 мс,
`events.size() == 100000`, `skipped == 0`.
