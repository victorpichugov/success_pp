# Лекция 11. Исключения: копирование, спецификации, конструкторы и деструкторы

> Аккуратный конспект лекции Ильи Мещерина по C++.
> Продолжение 10-й лекции: там разобрали синтаксис `throw`/`try`/`catch` и порядок выбора `catch`,
> здесь — **сколько копий создаётся**, как устроены **спецификации исключений**, и что происходит,
> если `throw` прилетает в **конструктор** или **деструктор**.
> Черновик лекции — в `readme.md` рядом.

> Контекст от лектора: **в Яндексе исключениями пользуются, в Google — нет.**
> Оба подхода рабочие, поэтому на собеседовании спрашивают не «нужны ли исключения»,
> а **как они работают изнутри** — этим и займёмся.

## 1. Повтор: порядок обработки исключений (вопрос на собесе)

```cpp
try {
    ...
} catch (double d) {
    std::cout << "2";
} catch (int x) {
    std::cout << "3";
} catch (...) {}
```

**Вопрос:** в `try` я бросил `int` — напечатается `2` или `3`?

**Ответ:** напечатается **только `2`**. Выбор идёт по **первому подходящему** `catch`,
а `int` → `double` — допустимое неявное преобразование, поэтому первая ветка подходит.
Ветка `catch (int)` не выполняется **вообще**, до неё не доходит.

Отсюда три правила порядка `catch`:

- от **частных** типов к **общим**;
- `catch (...)` — всегда **последним** (всё после него мертво);
- иерархию исключений тоже сортируем: потомки → `std::exception` → `...`.

### 1а. Проброс исключения дальше

Из `catch` можно бросить исключение **выше** — для этого есть «голый» `throw;`:

```cpp
// Вариант 1
try {
    ...
} catch (...) {
    ...            // залатать ресурсы / залогировать

    throw;         // пробросить TO ЖЕ САМОЕ исключение наверх
}
```

> Разница между `throw;` и `throw e;` появится в §3 — это один из самых частых
> вопросов на собеседованиях по исключениям.

## 2. Исключение — это **копия**

Мейерс (Effective C++, правило 13) пишет: **когда вы бросаете исключение, компилятор
создаёт его копию**, независимо от того, как объект был создан.

Почему: при выходе из блока все локальные объекты **уничтожаются**. Если бы в `catch`
улетал оригинал, он был бы уже мёртв (`s` живёт только внутри `try`). Поэтому брошенный
объект копируется в **специальное место** («статическое»/стационарное хранилище исключений),
живущее вне стека текущего блока, — и именно оно попадает в параметр `catch`.

### 2а. Считаем конструкторы

```cpp
try {
    String s;        // конструктор №1: локальный s
    throw s;         // конструктор №2: КОПИЯ брошенного объекта
} catch (String& s) {
    ...              // bind по ссылке — копий НЕТ
    throw;
}
```

**Ответ на вопрос «сколько раз вызовется конструктор `String`»:**
**2 раза** — один на `String s;` и один на копию брошенного объекта.
`throw;` **копию не создаёт**.

### 2б. Ловля по значению — 3 копии

```cpp
try {
    String s;        // конструктор №1
    throw s;         // конструктор №2 (копия брошенного)
} catch (String s) { // конструктор №3 (копия в параметр по значению)
    ...
    throw;
}
```

**Три конструктора.** Отсюда практическое правило:

> **Бросаем по значению, ловим по `const`-ссылке**: `catch (const std::exception& e)`.
> Ловля по значению = лишние копии + **срезка** производного класса.
> Ловля по `&`/`const&` — без копий и без срезки.

## 3. `throw;` vs `throw f;` (слайсинг в исключениях)

Даны классы `Base`/`Derived`. Возьмём из лекции: `Fish` — база, `Perch` — потомок.

### Пример 1 — падает

```cpp
try {
    Perch d;
    Fish& b = d;
    throw b;                 // бросаем ПО СТАТИЧЕСКОМУ ТИПУ: Fish
} catch (Fish& f) {
    dynamic_cast<Perch&>(f); // bad_cast!
}
```

**Падает**, потому что при `throw` компилятор **не задумывается над типами**:
тип брошенного объекта — **статический** тип выражения (`Fish`), а не реальный (`Perch`).
В «стационарное» хранилище уезжает **объект типа `Fish`** (фактически — срезанный),
таблица виртуальных функций у него от `Fish`, и `dynamic_cast<Perch&>` закономерно
бросает `std::bad_cast`.

> Момент про vtable: брошенный объект — полноценный `Fish`, его vtable указывает на
> `Fish`-версии методов. Никакой «памяти о `Perch`» в нём не осталось.

### Пример 2 — «всё сработает» (формулировка лекции)

```cpp
try {
    Perch d;
    Fish& b = d;
    throw b;
} catch (Fish& f) {
    dynamic_cast<Perch&>(f);
    throw f;                 // бросаем по СТАТИЧЕСКОМУ типу f, т.е. Fish
}
```

Лектор помечает этот вариант как рабочий (в `catch` есть `dynamic_cast`, и дальше
бросается объект того статического типа, который мы реально держим). Ключевой вывод,
который надо запомнить: **`throw <переменная>` всегда смотрит на статический тип
переменной, а не на тип объекта, в который она «смотрит».**

> **Честное замечание (проверено поведению, а не формулировке):** раз срезка происходит
> в момент `throw b;`, в `catch` прилетает **объект типа `Fish`**, и `dynamic_cast<Perch&>`
> в примере 2 тоже бросит `bad_cast`. Чтобы каст сработал, бросать надо **реальным**
> типом: `throw d;` (тогда летит `Perch`, `catch (Fish&)` примет, `dynamic_cast<Perch&>` — OK)
> или, для полиморфных классов, кидать производное исключение и ловить его по `const&`
> на базе — тогда срезки нет, потому что ловля **по ссылке** её не делает.

### Пример 3 — `throw;` не создаёт копий

```cpp
try {
    Perch d;
    Fish& b = d;
    throw b;
} catch (Fish& f) {
    ...
    throw;                   // НЕ создаёт копий, отправляет в полёт то, что уже летело
}
```

> **Чем `throw;` отличается от `throw f;`:** `throw;` **не создаёт никаких копий** и
> отправляет в полёт **тот самый объект, который уже в полёте** (с его исходным
> статическим типом). `throw f;` — это **новый** `throw`: создаётся **новая копия**
> по статическому типу `f`.

Практический вывод: **для проброса пиши `throw;`**, а не `throw e;`.

## 4. Спецификации исключений — старая версия (до C++11)

```cpp
// функция может кидать исключения из списка
void f(...) const throw(T1, T2) { }

// обещание себе и компилятору: исключения НЕ полетят НИКОГДА
void f(...) const throw() { }
```

Если обещание нарушено:

```cpp
void f(...) const throw() {
    throw 1;                 // обещание нарушено
}
```

→ **runtime error** (не ошибка компиляции): вызывается `std::unexpected`, по умолчанию
она зовёт `std::terminate`, программа падает. В C++98 можно было подменить обработчик
(`std::set_unexpected`), в C++11 вся эта конструкция **устарела**, в C++17 **удалена**
(кроме пустого `throw()`, который теперь означает `noexcept`).

## 5. Спецификации исключений — C++11: `noexcept`

`noexcept` — **спецификатор**: слово, которое пишется после параметров функции
(«перед телом»), и обещает, что функция не бросает.

```cpp
void f(T x) noexcept {
    throw 1;      // НЕ рантайм-ошибка: компилятор это заметит (warning/ошибка логики),
}                 // а при реальном броске — std::terminate
```

- компилятор **статически** видит `throw` внутри `noexcept`-функции → это **ошибка на
  этапе компиляции** (в коде так писать нельзя), а не поздний runtime error, как в старом `throw()`;
- если исключение вылетит из `noexcept`-функции «изнутри» (из вызванной функции) →
  сразу **`std::terminate`**, без размотки.

### 5а. условный `noexcept` и оператор `noexcept`

Проблема: внутри `f` мы вызываем чужие функции, и по ним непонятно, бросают они или нет.

```cpp
void f(T x) noexcept {
    g(x);   // версия для int бросает, остальные — нет
}
```

Для этого есть **оператор** `noexcept(...)` — выражение, дающее `true`/`false`:

```cpp
void f(T x) noexcept(noexcept(g(x))) {
    g(x);
}
```

> **Спецификатор** `noexcept` — слово в сигнатуре (обещание).
> **Оператор** `noexcept(...)` — выражение, вычисляемое **на этапе компиляции**:
> «может ли это выражение бросить исключение?».
> Комбинация `noexcept(noexcept(g(x)))` — стандартный идиоматический стиль:
> функция noexcept ровно тогда, когда noexcept её реализация.

```cpp
noexcept(fib(10) > 200 ? 1 : 0);   // выражение-проверка: вычисляется на компиляции,
                                   // само fib() в рантайме НЕ вызывается
```

## 6. Исключения в **конструкторах**

```cpp
struct Ugly {
    int* p;
    Ugly() {
        p = new int;
        throw 1;
    }
    ~Ugly() {
        delete p;
    }
};

int main() {
    try {
        Ugly u;
    } catch (...) {}
}
```

**Что здесь происходит?** — **утечка памяти**.

> **Исключение в конструкторе → деструктор НЕ вызывается.**
> Всё, что накопила конструктор (`new int`), не освобождается — оно просто теряется.

Важно: деструктор не вызывается для объекта, который **не достроился**; конструкторы
**базовых классов и полей**, которые уже отработали, — **свои деструкторы вызовутся**
(объект уничтожается ровно на той границе, которая была построена).

Конструкция вида

```cpp
void f() {
    p = new ...;
    throw ...;
    delete p;      // до сюда может дело не дойти
}
```

стремна **сразу**, ещё до всяких исключений.

### 6а. Идея спасения — RAII и умные указатели

Пример из лекции: класс, который занимается подключением по IP-сети —
в конструкторе «установи соединение с таким-то портом такого-то сервера»,
в деструкторе «разорви соединение».

> Идея: написать **специальный класс**, который в конструкторе **принимает указатель**,
> а в деструкторе делает `delete` по этому указателю. Это и есть **умные указатели
> (smart pointers)** — их цель: **решить проблему утечек памяти**.

**Сборка мусора в C++ есть?** — **Нет**, в C++ такого нет (в Java — есть).
В C++ за ресурсы отвечают **деструкторы** (RAII), а не сборщик.

### 6б. Как правильно бросать из конструктора

- все ресурсы — только через объекты-владелцы (умные указатели, контейнеры, lock'и);
- то, что может бросить, — **в списке инициализации** и в первых строках, до «ручных» `new`;
- если нужно сделать много шагов, каждый из которых может упасть — вынести в
  **фабричную функцию** (`static std::unique_ptr<C> create(...)`), а конструктор держать
  «тотальным» и простым;
- бросаем **свои** исключения, производные от `std::exception`, — вызывающий ловит по `const&`.

## 7. Исключения в **деструкторах**

```cpp
struct Ugly {
    int* p;
    Ugly() { p = new int; }
    ~Ugly() {
        delete p;
        throw 1;          // NEVER EVER
    }
};

int main() {
    try {
        Ugly u;
    } catch (...) {}      // деструктор бросит — выживание под вопросом
}
```

Смертельный сценарий:

```cpp
void f() {
    Ugly u;
    throw 1;              // начали размотку
}                         // при размотке вызывается ~Ugly() → ОН ТОЖЕ БРОСАЕТ
```

> Уничтожение локальных объектов при размотке стека → вызов деструкторов →
> а там **опять `throw`**. Исключение во время размотки = **`std::terminate`** (программа падает).

Поэтому Мейерс (More Effective C++, правило 11 / Effective Modern C++):

> **Никогда не бросайте `throw` в деструкторе. Не позволяйте исключениям покидать деструктор.**

Как безопасно:

```cpp
~File() noexcept {
    try {
        close();
    } catch (...) {          // глушим всё; в деструкторе нечего сообщать наружу
        // лог / игнор
    }
}
```

Полезные средства:

- **`std::uncaught_exceptions()`** (C++11, старый `std::uncaught_exception()` C++98) —
  «идёт ли сейчас размотка?». Костыль: если идёт — в деструкторе не бросаем, а молча
  латаем.
- **`std::terminate()`** — вызывается, когда продолжить нельзя; ей можно назначить
  свой обработчик (`std::set_terminate`), но спастись уже нельзя.

## 8. Гарантии безопасности при исключениях

Про «сильную» гарантию из лекции: **если операцию выполнить не удалось — всё остаётся
в порядке** (объект в прежнем состоянии, утечек нет). По Мейерсу три уровня:

| Уровень | Название | Что обещает |
|---|---|---|
| 0 | **базовая / нет гарантии** | объект остаётся **валидным** (не «мусор»), но в каком состоянии — неизвестно |
| 1 | **сильная** | **всё или ничего**: операция выполнена либо состояние **полностью прежнее** |
| 2 | **nothrow** | операция **не бросает вообще** (`noexcept`) |

Как достигается сильная гарантия — стандартная схема copy-and-swap:

```cpp
void Stack::push(const T& x) {
    std::vector<T> copy = data_;   // работаем на копии
    copy.push_back(x);             // если бросит — data_ не тронут
    data_.swap(copy);              // noexcept — точка невозврата
}
```

Инфраструктура, которая это обеспечивает:

- **Stack unwinding** — при подъёме к `catch` вызываются деструкторы всех локальных
  объектов на пути;
- **RAII** — ресурсы держим в объектах, чьи деструкторы их освобождают → утечки при `throw` нет.

## 9. За рамками лекции (что доучить по главе)

- **`std::nested_exception` / `std::throw_with_nested`** (C++11) — проброс с сохранением
  контекста.
- **Исключения дороги**: таблицы размотки, запрет части оптимизаций и инлайнинга вокруг
  `try` → в «горячих» путях их не используют (в том числе потому исключения не любят
  в игровых движках и в embedded).
- **Код ошибки vs исключение**: ожидаемые и частые ситуации (EOF, «не нашёл») — код ошибки
  / `std::optional`; редкие «аварии» (`bad_alloc`, парсинг config) — исключения.

> Задача после лекции: написать класс-владелец ресурса (файл/сокет) так, чтобы
> (1) бросок из конструктора не оставлял утечек, (2) деструктор был `noexcept`,
> (3) `push`-подобная операция давала сильную гарантию. Проверить через `-fsanitize=address`.
