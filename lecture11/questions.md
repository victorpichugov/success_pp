# Лекция 11. Исключения: копирование, `noexcept`, конструкторы и деструкторы — вопросы для практики

> Составлено по `final_readme.md`. Формулируй ответ сам, затем сверяйся с `<details>`.
> Вопросы с «что произойдёт»: сначала угадай (скомпилируется? сколько копий? упадёт?), потом открывай.

---

## Порядок обработки и проброс

### 1. Что напечатает этот код, если в `try` бросили `int`?

```cpp
try { ... }
catch (double d) { std::cout << "2"; }
catch (int x)     { std::cout << "3"; }
catch (...) {}
```

<details><summary>Ответ</summary>

Напечатается **только `2`**. Выбор идёт по **первому подходящему** `catch`, а `int → double` —
допустимое неявное преобразование, поэтому первая ветка подходит. До `catch (int)` дело не доходит.

</details>

### 2. Сформулируй правило порядка `catch`-блоков.

<details><summary>Ответ</summary>

От **частных** типов к **общим**; `catch (...)` — **последним**; иерархию исключений тоже
сортируем: потомки → `std::exception` → `...`. Всё, что стоит после подходящего `catch`, мертво.

</details>

### 3. Как из `catch` пробросить исключение наверх? Напиши код.

<details><summary>Ответ</summary>

```cpp
try {
    ...
} catch (...) {
    ...            // залатать ресурсы / залогировать
    throw;         // «голый» throw — пробросить ТО ЖЕ исключение выше
}
```

</details>

## Копирование при исключениях

### 4. Создаётся ли копия брошенного объекта? Всегда ли?

<details><summary>Ответ</summary>

Да, **всегда**: по Мейерсу компилятор создаёт **копию** брошенного объекта, независимо от того,
как он был создан. Причина: при выходе из блока локальные объекты уничтожаются, и оригинал к моменту
попадания в `catch` был бы мёртв. Копия кладётся в специальное хранилище исключений, живущее вне стека блока.

</details>

### 5. Сколько раз вызовется конструктор `String`?

```cpp
try {
    String s;
    throw s;
} catch (String& s) {
    ...
    throw;
}
```

<details><summary>Ответ</summary>

**Два раза**: (1) на `String s;`, (2) копия брошенного объекта. Параметр `catch (String&)` —
ссылка, копий не создаёт; `throw;` — тоже без копий.

</details>

### 6. А теперь сколько?

```cpp
try {
    String s;
    throw s;
} catch (String s) {
    ...
    throw;
}
```

<details><summary>Ответ</summary>

**Три**: локальный `s`, копия брошенного, копия в параметр `catch` **по значению**.

</details>

### 7. Как правильно бросать и как правильно ловить? Почему?

<details><summary>Ответ</summary>

Бросаем **по значению** (`throw MyExcp(...)`), ловим **по `const`-ссылке**
(`catch (const std::exception& e)`). По значению в `catch` — лишняя копия **плюс срезка**
производного класса (теряется `what()` потомка и всё его состояние).

</details>

## `throw;` vs `throw f;`

### 8. Даны `Fish` (база) и `Perch` (потомок). Что произойдёт?

```cpp
try {
    Perch d;
    Fish& b = d;
    throw b;
} catch (Fish& f) {
    dynamic_cast<Perch&>(f);
}
```

<details><summary>Ответ</summary>

Упадет в **`std::bad_cast`**. При `throw` компилятор **не задумывается над типами**: тип брошенного
объекта — **статический** тип выражения (`Fish`), а не реальный (`Perch`). В полёт уезжает объект
типа `Fish` (срезанный), его vtable — от `Fish`, поэтому каст вниз не проходит.

</details>

### 9. На каком типе объекта основан `throw <переменная>`?

<details><summary>Ответ</summary>

На **статическом** типе переменной (выражения). `Fish& b = d; throw b;` бросает `Fish`,
даже если `b` ссылается на `Perch`.

</details>

### 10. Чем `throw;` отличается от `throw f;`?

<details><summary>Ответ</summary>

`throw;` **не создаёт никаких копий** и отправляет в полёт **тот самый объект, который уже летит**,
с его исходным статическим типом. `throw f;` — **новый** бросок: создаётся **новая копия** по
статическому типу `f`. Вывод: для проброса пишем `throw;`.

</details>

### 11. Как бросить исключение так, чтобы в `catch` можно было восстановить производный тип?

<details><summary>Ответ</summary>

Либо бросать **объектом производного типа** (`throw d;` — тогда летит `Perch`, `catch (Fish&)`
примет, `dynamic_cast<Perch&>` пройдёт), либо (правильнее) кидать **производное исключение** и
ловить его **по ссылке на базу** — ловля по ссылке срезки не делает.

</details>

## Спецификации исключений

### 12. Как выглядели спецификации исключений до C++11? Напиши обе.

<details><summary>Ответ</summary>

```cpp
void f(...) const throw(T1, T2) { }   // могут летать только эти типы
void f(...) const throw()          { }   // обещание: исключения НЕ полетят никогда
```

</details>

### 13. Что будет, если нарушить старое обещание `throw()`?

```cpp
void f(...) const throw() { throw 1; }
```

<details><summary>Ответ</summary>

**Runtime error**, а не ошибка компиляции: вызывается `std::unexpected`, которая по умолчанию
зовёт `std::terminate` — программа падает. В C++11 конструкция устарела, в C++17 удалена
(пустой `throw()` ≡ `noexcept`).

</details>

### 14. Что такое `noexcept` и где он пишется?

<details><summary>Ответ</summary>

**Спецификатор** — слово после списка параметров функции (перед телом/`const`-частями), обещание
не бросать исключения: `void f(T x) noexcept { ... }`.

</details>

### 15. Что получим, если написать `throw` внутри функции с `noexcept`?

<details><summary>Ответ</summary>

Не поздний runtime error, а реакцию **на этапе компиляции** (компилятор видит бросок статически).
Если же исключение вылетит из `noexcept`-функции (из вызванной внутри) — размотки нет, сразу
**`std::terminate`**.

</details>

### 16. Внутри `f` вызывается `g(x)`: для `int` версия бросает, для остальных — нет. Как объявить `f`?

<details><summary>Ответ</summary>

```cpp
void f(T x) noexcept(noexcept(g(x))) {
    g(x);
}
```

Внешний `noexcept(...)` — **спецификатор**, внутренний — **оператор**. Функция `noexcept` ровно
тогда, когда `noexcept` её реализация.

</details>

### 17. Что такое `noexcept(...)`-оператор и когда он вычисляется? Пример.

<details><summary>Ответ</summary>

Это **выражение**, дающее `true`/`false`: «может ли данное выражение бросить исключение?».
Вычисляется **на этапе компиляции**, само выражение в рантайме **не выполняется**:

```cpp
noexcept(fib(10) > 200 ? 1 : 0);   // fib() НЕ вызывается, считается только «бросит/не бросит»
```

</details>

## Исключения в конструкторах

### 18. Что не так с этим кодом?

```cpp
struct Ugly {
    int* p;
    Ugly() { p = new int; throw 1; }
    ~Ugly() { delete p; }
};

int main() {
    try { Ugly u; } catch (...) {}
}
```

<details><summary>Ответ</summary>

**Утечка памяти.** Исключение в конструкторе → объект не достроен → **деструктор не вызывается**,
и всё, что накоплено в конструкторе (`new int`), теряется.

</details>

### 19. Деструкторы базовых классов и полей: вызываются ли они при броске из конструктора?

<details><summary>Ответ</summary>

Да — уничтожается ровно **построенная часть**: свои деструкторы вызовутся для базовых классов
и полей, чьи конструкторы уже завершились. Сам «недостроенный» объект не уничтожается (его и нет).

</details>

### 20. Почему конструкция `p = new ...; throw ...; delete p;` плоха?

<details><summary>Ответ</summary>

Она стрёмна **сразу**: до `delete` может не дойти ни при каком `throw` (а также при `return`,
`break`, вызове функции, которая бросит). `delete` не должен зависеть от «дожил ли код до строки».

</details>

### 21. Приведи пример класса-ресурса из лекции и идею спасения.

<details><summary>Ответ</summary>

Класс подключения к IP-сети: конструктор «установи соединение с портом/сервером», деструктор
«разорви». Идея: завести **специальный класс**, который в конструкторе **принимает указатель**,
а в деструкторе делает по нему `delete` — это **умные указатели**, их цель — решать проблему утечек.

</details>

### 22. Есть ли в C++ сборка мусора?

<details><summary>Ответ</summary>

**Нет.** В Java — есть, в C++ за ресурсы отвечают **деструкторы** (RAII) и умные указатели.

</details>

### 23. Как правильно бросать исключение из конструктора?

<details><summary>Ответ</summary>

- все ресурсы — только через объекты-владелцы (умные указатели, контейнеры, lock'и);
- бросать **рано**, до «ручных» `new`, — всё, что уже построено, отработает штатно;
- многошаговую инициализацию выносить в **фабричную функцию** (`static std::unique_ptr<C> create()`);
- бросать **свои** классы, производные от `std::exception`, чтобы ловили по `const&`.

</details>

## Исключения в деструкторах

### 24. Что происходит здесь?

```cpp
struct Ugly {
    int* p;
    Ugly() { p = new int; }
    ~Ugly() { delete p; throw 1; }
};

void f() {
    Ugly u;
    throw 1;
}
```

<details><summary>Ответ</summary>

Уничтожение локального объекта → вызов деструктора → а он **тоже бросает**. Получается исключение
**во время размотки стека** → **`std::terminate`**, программа падает (ловить уже нечем).

</details>

### 25. Сформулируй правило Мейерса про деструкторы. Как написать деструктор безопасно?

<details><summary>Ответ</summary>

**Никогда не бросай `throw` в деструкторе; не позволяй исключениям покидать деструктор.**

```cpp
~File() noexcept {
    try { close(); }
    catch (...) { /* лог / игнор */ }
}
```

</details>

### 26. Какие средства помогают понять, что идёт размотка, и что такое `std::terminate`?

<details><summary>Ответ</summary>

`std::uncaught_exceptions()` (C++11; старый `std::uncaught_exception()`) — «идёт ли сейчас
размотка?»; если да — в деструкторе не бросаем, а молча латаем. `std::terminate()` — вызывается,
когда продолжать нельзя; обработчик ставится через `std::set_terminate`, но спастись уже нельзя.

</details>

## Гарантии безопасности

### 27. Назови три гарантии безопасности при исключениях.

<details><summary>Ответ</summary>

1. **Базовая** — объект остаётся **валидным**, но в каком состоянии — неизвестно.
2. **Сильная** — «всё или ничего»: операция выполнена либо состояние **полностью прежнее**.
3. **nothrow** — операция **не бросает вообще** (`noexcept`).

</details>

### 28. Как реализуется сильная гарантия? Приведи код.

<details><summary>Ответ</summary>

Схема **copy-and-swap**: работаем на копии, меняем оригинал только операцией, которая не бросает.

```cpp
void Stack::push(const T& x) {
    std::vector<T> copy = data_;   // если бросит — data_ не тронут
    copy.push_back(x);
    data_.swap(copy);              // noexcept — точка невозврата
}
```

Инфраструктура: **stack unwinding** (деструкторы локальных объектов на пути к `catch`) + **RAII**.

</details>

## Итоговый вопрос

### 29. Ответь «в одну строку» на четыре вопроса про исключения: (1) копия при `throw`, (2) `throw;` vs `throw e;`, (3) бросок в конструкторе, (4) бросок в деструкторе.

<details><summary>Ответ</summary>

(1) Брошенный объект **всегда копируется** в хранилище исключений — оригинал умирает при выходе из блока.
(2) `throw;` — **без копий**, летит исходный объект; `throw e;` — новый бросок и **новая копия** по
статическому типу `e` (отсюда срезка).
(3) В конструкторе бросать **можно**: деструктор этого объекта не вызовутся → держим ресурсы в RAII,
иначе утечка.
(4) В деструкторе бросать **нельзя**: исключение при размотке → `std::terminate`; внутри `try { } catch (...) {}`.

</details>
