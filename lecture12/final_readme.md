# Лекция 12. Оператор `new`, перегрузка `new`/`delete`, аллокаторы

> Аккуратный конспект лекции Ильи Мещерина по C++.

> **аллокаторы**. Они нужны, чтобы потом писать **свои контейнеры**: `vector`, `list`, `deque`,

## 1. Дополнение к 11-й лекции: стандартные исключения

Есть **готовые** классы исключений — изобретать свои для типовых ситуаций не надо.
Заголовок `<exception>` (в старом написании `exception.h`):

```
                std::exception            // базовый класс, метод what()
                /        |        \
        bad_alloc   logic_error   runtime_error
                        |              |
              invalid_argument     (что-то пошло при выполнении)
              out_of_range
```

- **`std::exception`** — базовый; у него есть метод **`what()`**, возвращающий строку
  (`const char*`) с описанием того, **что случилось**;
- **`std::bad_alloc`** — его бросает обычный `new`, когда память выделить не удалось;
- **`std::runtime_error`** — ошибки, которые обнаруживаются только при выполнении
  (`std::runtime_error("соединение потеряно")`);
- **`std::logic_error`** — ошибки в логике программы (неверный аргумент, нарушение
  предусловия): `invalid_argument`, `out_of_range`, `length_error`.

```cpp
try {
    int* p = new int[1'000'000'000L];
} catch (const std::bad_alloc& e) {
    std::cout << e.what();       // что случилось
} catch (const std::exception& e) {
    std::cout << e.what();       // всё остальное из иерархии
}
```

> Ловим по **`const&`** (11-я лекция): по значению — копия + срезка, `what()` потомка потеряется.

## 2. Зачем нужны аллокаторы

Тема нужна, чтобы понимать, **как контейнеры размещают объекты в памяти**, и уметь писать свои.

- `vector`, `list`, `deque`, `map`, `set` и т. д. принимают **аллокатор одним из
  шаблонных параметров**:

```cpp
std::vector<int> v;                                  // аллокатор по умолчанию
std::vector<int, MyAlloc<int>> v2;                   // свой аллокатор
std::list<int, MyAlloc<int>> l;
```

- сам контейнер **не вызывает `new` напрямую**: он делает это через **прослойку**, которая
  обращается к `new` аккуратно. Прослойка — **аллокатор**.

---

## 3. Разделение: «выделить память» и «построить объект»

Ключевая идея всей темы: в C++ создание объекта — это **два независимых шага**.

1. **выделить память** под объект (сырой, неконструированной);
2. **вызвать конструктор** в этом месте;

и симметрично при уничтожении: сначала **деструктор**, потом **освободить память**.

### 3а. Задача: положить элемент в уже выделенную память

`push_back()` в `vector`: память **уже выделена** (вместимость > размера), осталось
**положить элемент**. А чтобы положить — надо **вызвать конструктор**. Как явно вызвать
конструктор в нужном месте?

**`placement new`** — один из ~15 видов оператора `new`:

```cpp
new (p) T(args...);   // берёт указатель p и по этому адресу вызывает конструктор T;
                      // ПАМЯТЬ НЕ ВЫДЕЛЯЕТ — только конструирует
```

### 3б. А как вызвать деструктор?

Явно, руками — он обычно не вызывается, потому что память под объектом не «стековая»:

```cpp
p->~T();      // явный вызов деструктора по адресу
```

> **Правило пары:** сделали `new (p) T(...)` → обязаны сами сделать `p->~T();`.
> Никто за вас это не сделает, и `delete p` к placement-объекту применять **нельзя**.

## 4. Перегрузка оператора `new`

Мотивация: хочу выделять память **по-особенному** — например, заранее попросить 2 ГБ,
а потом самому решать, как её распределять (свой менеджер памяти). Это позволяет
**перегрузить `operator new`**.

### 4а. Глобальная перегрузка

```cpp
size_t — беззнаковый целочисленный тип (размер в байтах)

void* operator new(size_t n) {
    ...                      // своя стратегия выделения
}
```

### 4б. Членская перегрузка (на уровень класса)

```cpp
class C {
    static void* operator new(size_t n) {
        ...                                  // как выделить память?
    }
};
```

Функция **обязана быть `static`** — объекта ещё нет, `this` брать не откуда.
Изнутри зовём **глобальную** версию, иначе рекурсия:

```cpp
class C {
    static void* operator new(size_t n) {
        return ::operator new(n);            // глобальный вызов оператора new
    }
};
```

### 4в. Менеджер памяти в две строки

Идея из лекции: при **первом** вызове — увеличить счётчик и выделить **большой кусок**
памяти; если вызов уже был (кусок ≠ `nullptr`) — просто **распределять** внутри
уже выделенного куска. Так получается «пул» без системных вызовов на каждое выделение.

### 4г. Что на самом деле делает оператор `new`

Глобальный `new` делает **две вещи**:

1. **вызывает функцию `operator new`** с соответствующими параметрами — **её можно перегрузить**;
2. **по тому, что она вернула, вызывает конструктор** — **этого перегрузить нельзя**.

```
int* p = new int(5);
        ↓
   1) operator new(sizeof(int))  →  void*            (перегружаемо)
   2) конструктор int(5) по этому адресу             (НЕ перегружаемо)
```

Отсюда: перегружая `operator new`, вы управляете **только памятью**, а не конструированием.

### 4д. Перегрузка placement new

Я перегрузил форму `new (p) T(...)`:

```cpp
static void* operator new(size_t n, void* p) {
    return p;            // вот ответ на «вопрос на понимание»
}
```

> **Вопрос на понимание:** что должна делать перегрузка placement-`new`?
> **Ответ: ничего не выделять и вернуть переданный указатель как есть.** Вся её суть —
> вернуть адрес, на котором потом вызовется конструктор.

### 4е. Аналогично — `delete`

Оператор `delete` тоже делает **2 вещи**:

1. **вызывает деструктор** по адресу, который сказали;
2. **освобождает память**.

Но с `delete` всё сложнее: **нельзя** написать `delete(...) p;` — такого синтаксиса нет.
Явный вызов формы с параметрами — через глобальную функцию:

```cpp
::operator delete(p);          // освобождение памяти (деструктор — отдельно, руками)
```

### 4ж. Парные параметры: `new (p, 2) T(...)`

Хочу конструировать объект с какими-то спецпараметрами:

```cpp
new (p, 2) T(...);     // вызовет operator new(size_t, void*, int)
```

Как тогда уничтожать объект?

```cpp
p->~T();               // НЕДОСТАТОЧНО — так писать неправильно!
```

> Надо **так**: сначала **явно вызвать деструктор**, потом **явно вызвать `delete`
> с теми же параметрами, с которыми вызывали `new`**:

```cpp
p->~T();                       // 1) деструктор
::operator delete(p, 2);       // 2) освобождение « теми же аргументами»
```

### 4з. Массивы

**`operator new[]` и `operator delete[]` перегружаются отдельно** (у них своя сигнатура,
они работают с массивами). Форма с параметрами для массивов:
`new (p, 2) T[n]` ↔ `::operator delete[](p, 2)`.

### 4и. Совет Мейерса (Effective C++, правило 10)

> Если вы реализовали **кастомный `new`**, реализуйте **такой же кастомный `delete`
> с теми же параметрами**. Иначе память, выделенная вашей стратегией, будет освобождена
> чужой — UB.

### 4к. Полиморфный `delete`

```cpp
class Base {
public:
    ~Base() {}                    // НЕ virtual!
    int x;
};

class Derived : public Base {
    int y;
};

Base* bd = new Derived;
delete bd;      // какой delete вызовется?
```

`operator new`/`operator delete` — функции **статические** (перегрузка решается по
**статическому** типу: у `Base` — своя, у `Derived` — своя, `delete bd` зовёт `Base`-версию).
Но **какой деструктор** вызвать внутри освобождения — решается **динамически**, и вызывается
**полиморфный деструктор**, т. е. нужен `virtual ~Base()`.

> Итог: **память** освобождается по статическому типу, **деструктор** — по динамическому.
> Без `virtual ~Base()` — UB + утечка `y` (тема 8-й лекции).
> Плюс тонкость с массивами: `new Derived[n]` + `delete[] bd` тоже требует виртуального
> деструктора, потому что для массивов нужно «спрятать» количество элементов рядом с памятью.

## 5. `nothrow`-новая форма

Она **не бросает исключение**, а возвращает **`nullptr`** (10-я лекция, `bad_alloc`):

```cpp
int* p = new (std::nothrow) int[1000];
if (p == nullptr) { /* не хватило памяти */ }
```

Её реализация — одна из форм `operator new`:

```cpp
void* operator new(size_t n, const std::nothrow_t&) noexcept {
    ...                 // пытаться выделить; не вышло — вернуть nullptr
}
```

Нужны заголовки: **`#include <new>`** (все формы `new`/`delete`, `nothrow`, placement)
и **`#include <memory>`** (умные указатели, `allocator`, `uninitialized_*`).

## 6. `new_handler`

Механизм: «не хватает памяти — **попроси ещё и попробуй снова**».

```cpp
void my_handler() { ... }              // что делать при нехватке памяти

std::set_new_handler(my_handler);      // назначить обработчик
std::get_new_handler();                // узнать текущий
```

Как это работает: `operator new` не смог выделить → вызывает `new_handler` →
если handler вернул управление, **пробует ещё раз**; если handler **не назначен**
(`set_new_handler(nullptr)`) → бросается `std::bad_alloc`. В handler можно: выделить память
у себя из запаса, назначить новый handler (`set_new_handler(nullptr)` — сдаться),
бросить своё исключение, вызвать `exit`.

> **Рекомендация лектора: вообще не перегружать `new` и `delete` явно — лучше
> использовать аллокаторы.** Глобальная перегрузка `new`/`delete` влияет на **всю
> программу** (включая библиотеки), это «программный уровень», а аллокатор — локальный
> и типобезопасный.

## 7. Аллокаторы

> **Аллокатор — это шаблонный класс, который маскирует (оборачивает) вызовы `new` и `delete`.**

Стандартный аллокатор, 4 основных метода:

```cpp
template <class T>
struct allocator {
    typedef T value_type;

    T* allocate(size_t n) const {
        return static_cast<T*>(::operator new(n * sizeof(T)));   // память
    }
    void deallocate(T* p, size_t n) const {
        ::operator delete(p);                                     // память
    }
    template<typename... Args>
    void construct(T* p, const Args&... args) const {
        return ::new (static_cast<void*>(p)) T(args...);          // конструктор
    }
    void destroy(T* p) const {
        p->~T();                                                  // деструктор
    }
};
```

(в черновике лекции написано `new char[n*sizeof(T)]` / `delete[] char* p` — по сути
то же самое: **память как байты, объект поверх неё**; в реальности — `::operator new` /
`::operator delete`; `construct`/`destroy` в C++17 **устарели**, в C++20 **удалены**.)

### 7а. Вопросы по `const`

> **Какие методы `const`, какие нет?** — Можно **все**: аллокатору **пофиг**, у него
> ничего не меняется, **даже полей нет**. Аллокатор — **stateless** «функция-обёртка»,
> вся его конфигурация — в **типе**, а не в состоянии.

Из этого следует важное: **аллокаторы обязаны быть взаимозаменяемыми и не иметь состояния**
(иначе `deallocate` из «другого» аллокатора ломается).

### 7б. `value_type`

У аллокатора **обязан** быть `typedef T value_type;` — по нему контейнер узнаёт,
для какого типа всё это.

### 7в. Что обязательно в своём аллокаторе

1. **`allocate` / `deallocate`** — обязательно (это и есть контракт аллокатора);
2. **`construct` / `destroy`** — **в будущем они не нужны**: в C++17 объявлены
   устаревшими, в C++20 удалены; контейнеры вызывают конструктор/деструктор сами
   через `std::allocator_traits` (который подставит placement new и `p->~T()` по умолчанию);
3. **`value_type`** — typedef;
4. конструктор копирования, `operator==`/`operator!=`, шаблонный конструктор
   `template<class U> MyAlloc(const MyAlloc<U>&)` — для `rebind`.

### 7г. `std::allocator_traits` — прослойка, к которой обращается контейнер

```cpp
template<class Alloc>
struct allocator_traits;
```

> **Именно к `allocator_traits` обращается `vector`**, а не к аллокатору напрямую.

```cpp
template<class Alloc>
struct allocator_traits {
    using value_type = typename Alloc::value_type;

    static value_type* allocate(Alloc& a, size_t n);          // a.allocate(n)
    static void deallocate(Alloc& a, value_type* p, size_t n); // a.deallocate(p, n)
    template<class T, class... Args>
    static void construct(Alloc& a, T* p, Args&&... args);     // ::new ((void*)p) T(...)
    template<class T>
    static void destroy(Alloc& a, T* p);                       // p->~T()

    template<class U> using rebind = typename Alloc::template rebind<U>::other;
    static size_type max_size(const Alloc& a);                 // size_t / sizeof(T)
};
```

Зачем прослойка:

- контейнер пишет код **один раз**, не зная, что за аллокатор;
- `traits` даёт **значения по умолчанию**: у аллокатора нет `construct` → traits сам
  сделает placement new; нет `max_size` → посчитает `SIZE_MAX / sizeof(T)`;
- `rebind` — «тот же аллокатор, но для другого типа»: `vector<Node<T>>` внутри
  `map`/`list` нуждается в `Alloc<Node<T>>` из `Alloc<T>`.

## 8. Как это выглядит в своём контейнере (сборка всей схемы)

```cpp
template<class T, class Alloc = std::allocator<T>>
class MyVector {
    using traits = std::allocator_traits<Alloc>;
    typename traits::pointer data_;      // память (сырая)
    size_t size_, cap_;
public:
    void push_back(const T& x) {
        if (size_ == cap_) grow();                          // allocate(cap_)
        traits::construct(alloc_, &data_[size_], x);        // конструктор В памяти
        ++size_;
    }
    ~MyVector() {
        for (size_t i = 0; i < size_; ++i)
            traits::destroy(alloc_, &data_[i]);             // деструкторы по одному
        traits::deallocate(alloc_, data_, cap_);            // память
    }
};
```

Порядок **«память → конструкторы → деструкторы → память»** — ровно то, за чем аллокаторы
и нужны; плюс он даёт **гарантию безопасности** (11-я лекция): если конструктор `x`
бросил — память уже выделена и будет освобождена деструктором контейнера, утечки нет.

### 8а. За рамками лекции (что доучить)

- **`std::pmr`** (C++17, `<memory_resource>`) — «полиморфные» аллокаторы через
  `memory_resource` (`monotonic_buffer_resource`, `pool_options`): состояние **в рантайм-объекте**,
  а не в типе — векторы с разными ресурсами совместимы по типу;
- **stateful allocators** и их ограничения (`propagate_on_container_copy/swap/move_assignment`);
- `std::uninitialized_fill`, `std::uninitialized_copy`, `std::uninitialized_default_construct`;
- аллокаторы в контейнерах — параметр шаблона → **разные аллокаторы = разные типы контейнера**
  (`vector<int, A>` и `vector<int, B>` не конвертируются друг в друга);
- `std::allocate_shared`/`std::make_unique` — та же тема выделения памяти «под ключ».

> Задача после лекции: реализовать свой **пул-аллокатор** (просим большой кусок, режем
> по `sizeof(T)`), подключить его к `std::vector` и сравнить скорость с `std::allocator`
> на 10⁶ `push_back`. Проверить утечки через `-fsanitize=address`.

|---|---|
| **Стандартные исключения** | `<exception>`: `std::exception` (метод `what()`), `bad_alloc`, `logic_error`, `runtime_error` |
| **Зачем аллокаторы** | Чтобы писать контейнеры; `vector`/`list`/`deque`/`map`/`set` принимают аллокатор параметром шаблона |
| **Прослойка** | Вектор **не зовёт `new` напрямую**, а через аллокатор |
| **Два шага** | создание объекта = **выделить память** + **вызвать конструктор**; уничтожение = **деструктор** + **освободить** |
| **`new (p) T(...)`** | **placement new**: конструирует по адресу `p`, память **не выделяет** |
| **`p->~T()`** | явный вызов деструктора; для placement-объектов — **обязательно руками** |
| **`void* operator new(size_t n)`** | глобальная перегрузка; `size_t` — беззнаковый «размер в байтах» |
| **Членская перегрузка** | `static void* operator new(size_t n)` внутри класса; внутри зовёт `::operator new(n)` |
| **Менеджер памяти** | первый вызов — выделить большой кусок; дальше — распределять внутри него |
| **Что делает `new`** | 1) вызывает **функцию** `operator new` (**можно** перегрузить); 2) вызывает **конструктор** (**нельзя** перегрузить) |
| **Перегрузка placement** | `static void* operator new(size_t, void* p) { return p; }` — ничего не выделяет, возвращает адрес |
| **Что делает `delete`** | 1) деструктор по адресу; 2) освобождение памяти |
| **`delete (p) x;`** | **такого синтаксиса нет** → явно: `::operator delete(p)` |
| **`new (p, 2) T(...)`** | уничтожать: `p->~T();` **+** `::operator delete(p, 2);` (те же параметры!) |
| **`new[]`/`delete[]`** | перегружаются **отдельно**, своей сигнатурой |
| **Мейерс** | сделал кастомный `new` → сделай **парный `delete` с теми же параметрами** |
| **`delete bd` (`Base*` → `Derived`)** | функция `operator delete` — **статическая** (статический тип), **деструктор** — **полиморфный** (`virtual ~Base`) |
| **`new (std::nothrow) T()`** | не бросает, возвращает **`nullptr`**; форма `operator new(size_t, const nothrow_t&)` |
| **Заголовки** | `<new>` (формы new/delete, nothrow), `<memory>` (аллокаторы, умные указатели) |
| **`new_handler`** | `std::set_new_handler` / `std::get_new_handler`; handler → `operator new` пробует **ещё раз** |
| **Не перегружай `new`/`delete`** | рекомендация: используй **аллокаторы** (локально и типобезопасно) |
| **Аллокатор** | шаблонный класс, **маскирующий вызовы `new`/`delete`** |
| **4 метода** | `allocate(n)`, `deallocate(p, n)`, `construct(p, args...)`, `destroy(p)` |
| **`const`** | можно **все** методы `const`: у аллокатора **нет состояния** (полей) |
| **`value_type`** | обязательный `typedef T value_type` |
| **Свой аллокатор** | обязательно `allocate`/`deallocate`; `construct`/`destroy` — **не нужны** (C++17 deprecated, C++20 удалены) + `rebind` |
| **`allocator_traits`** | **к нему обращается `vector`**; даёт значения по умолчанию и `rebind` |
| **`rebind<U>::other`** | «тот же аллокатор, но для `U`» — нужно спискам/деревьям внутри контейнеров |
| **Разные аллокаторы** | `vector<int, A>` и `vector<int, B>` — **разные типы** |
| **C++17 замена** | `std::pmr` + `memory_resource` — состояние аллокатора в рантайме, а не в типе |
