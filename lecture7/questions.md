# Лекция 7. Наследование — вопросы для практики

> Составлено по `final_readme.md`. Формулируй ответ сам, потом сверяйся с `<details>`.
> Многие вопросы — «что произойдёт»: сначала угадай ответ, потом открой.

---

## Поиск имён, hiding, `using`

### 1. Почему `d.f();` — ошибка, если в `Derived` есть `f(int)`, а в `Base` — `f()`?

<details><summary>Ответ</summary>

Как только в `Derived` появляется имя `f`, компилятор **не ищет** `f` в `Base` — это **hiding**
(сокрытие): все одноимённые методы предка прячутся, перегрузка «между классами» не работает
автоматически. `f(int)` без аргумента не подходит → ошибка.

</details>

### 2. Как явно вызвать скрытый метод предка? В чём ограничение по доступу?

<details><summary>Ответ</summary>

Квалифицированный вызов: `d.Base::f(5);`. Но если наследование **приватное** — даже так нельзя:
у внешнего кода нет прав обращаться к родителю. Возможны два разных сообщения:
«не видна область» (имя не найдено) и «недоступно» (inaccessible — найдено, но права запрещают).

</details>

### 3. Что делает `using Base::f;` в теле производного класса?

<details><summary>Ответ</summary>

Подтягивает **все** перегрузки `f` из `Base` в область видимости `Derived`, и нормальная
перегрузка начинает работать: `d.f();` и `d.f(5);` — оба ОК.

</details>

### 4. Каверзный вопрос: если не написать `public`/`private`/`protected` в спецификации наследования — что будет?

<details><summary>Ответ</summary>

Зависит от ключевика:

```cpp
struct Derived : Base { };   // по умолчанию public (как поля в struct)
class  Derived : Base { };   // по умолчанию private (как поля в class)
```

</details>

### 5. В каком порядке компилятор анализирует выражение: сначала поиск имени или сначала проверка доступа?

<details><summary>Ответ</summary>

Сначала **поиск имени** (какие кандидаты подходят по сигнатуре), **потом** проверка доступа.
Ключевое отличие от интуитивной «сначала права» логики.

</details>

### 6. `struct Base { void f() {} }; struct Derived : Base { private: void f(int) {} };` — почему `d.f()` ошибка?

<details><summary>Ответ</summary>

1. Поиск имени: кандидат для `d.f()` только `Derived::f(int)` — не подходит по сигнатуре, а `Base::f()`
   скрыт hiding'ом.
2. Поиск не привёл к подходящему кандидату → ошибка на этапе поиска (доступ к `Base::f()` тут и не
   проверяется — он бы и был публичным).

</details>

## Двухуровневое наследование, друзья

### 7. `Granny → private → Mom → public → Son`. Что доступно из `s.a;`, `s.b;`, `s.Mom::b;`, `s.Granny::a;`?

<details><summary>Ответ</summary>

- `s.c;` — OK (своё);
- `s.b;` — OK (public-наследование `Mom → Son`);
- `s.a;` — **ошибка**: `Granny` для `Son` скрыта приватным наследованием в `Mom`;
- `s.Mom::b;` — OK (явный квалификатор на видимый уровень);
- `s.Mom::Granny::a;` — **ошибка**: `Mom` не имеет права «выдавать» `Granny`;
- `s.Granny::a;` — **ошибка**: имя `Granny` вообще не видно в `Son`.

</details>

### 8. Запрет на скрытую базу распространяется только на поля? Можно ли объявить внутри `Son` `Granny g;`?

<details><summary>Ответ</summary>

Нет, запрет на **сам тип** предка: внутри `Son` и в сигнатурах функций `Granny g;`, `Granny&`,
`Granny*` — всё ошибка («тип не виден»). Просто «написать имя в глобальной области» тоже не сработает
— видимость идёт по цепочке наследования.

</details>

### 9. Как обойти запрет и сослаться на `Granny` из `Son`?

<details><summary>Ответ</summary>

Явно уйти в глобальную область: `void f(::Granny& g) { ... }`. Нужен именно `::Granny` —
обычное написание имени из тела `Son` не находит тип.

</details>

### 10. `Granny` сделал `friend class Son;`, но `Mom : private Granny`. Снимет ли это запрет на `s.Granny::...`?

<details><summary>Ответ</summary>

**Нет.** Запрет наложен **`Mom`** (приватным наследованием), а не `Granny` — «дружба с бабушкой»
не снимает запрет мамы. Если **`Mom`** сделает `friend class Son;` — запрет снят: `Son` «проходит»
через маму к бабушке.

</details>

### 11. Дружба транзитивна? Что видит друг класса?

<details><summary>Ответ</summary>

**Не транзитивна.** Другу класса доступно **всё то, что доступно самому классу** — и только.
Если `f()` — друг `Mom`, он видит `m.a` (потому что у `Mom` есть доступ к `protected a`), но это не
означает, что `f()` — друг `Granny`: будь `a` приватным у `Granny` — доступ запрещён.

</details>

## Конструкторы/деструкторы и размер объекта

### 12. Из чего «состоит» объект производного класса в памяти?

<details><summary>Ответ</summary>

**Объект базового класса + дописанные поля**:

```
| базовая часть (Granny) | производная часть (Mom) |
```

</details>

### 13. `Granny` имеет только конструктор `Granny(int)`. Скомпилируется ли `Mom(int b) : b(b) {}`? Почему?

<details><summary>Ответ</summary>

**Нет.** При конструировании `Mom` компилятор обязан сконструировать базовую часть, но конструктор
по умолчанию у `Granny` не сгенерирован (есть `Granny(int)`) — подходящего конструктора без аргументов
нет. Если бы в `Granny` конструкторов с аргументами не было — дефолтный сгенерировался бы сам,
и код скомпилировался.

</details>

### 14. Как правильно инициализировать базовую часть? Что **нельзя** делать в init-list?

<details><summary>Ответ</summary>

Явно вызвать конструктор базы в init-list: `Mom(int b) : Granny(0), b(b) {}`.
Нельзя инициализировать **поле предка** как своё: `Mom(int a, int b) : a(a), b(b)` — ошибка,
`a` не своё поле. Можно инициализировать только **свои поля** + явно вызвать конструктор **своего**
(прямого) предка.

</details>

### 15. Может ли `Son` инициализировать `Granny` напрямую в своём конструкторе?

<details><summary>Ответ</summary>

**Нет**: «Granny is not a direct base of Son». Инициализировать можно **только прямых предков**.
Сын управляет своим прямым предком (`Mom`); как инициализировать бабушку — вопрос конструкторам `Mom`.

</details>

### 16. В каком порядке вызываются конструкторы и деструкторы в цепочке «бабушка → мама → сын»?

<details><summary>Ответ</summary>

**Конструкторы:** база → производный (бабушка → мама → сын).
**Деструкторы:** обратный порядок (сын → мама → бабушка). Это «стек»: конструкторы снизу вверх,
деструкторы сверху вниз.

</details>

### 17. Два `int` в разных классах цепочки `Granny → Mom`. Каков `sizeof(Mom)`?

<details><summary>Ответ</summary>

`sizeof(Mom) = 8` (4 + 4) — без сюрпризов выравнивания. Размер производного = размер базовой части
+ свои поля.

</details>

## Множественное наследование

### 18. Почему у `Square : Rhombus, Rectangle` (оба от `Parallelogram`) `s.x;` — ошибка?

<details><summary>Ответ</summary>

`Parallelogram` **дублируется** — по экземпляру в каждом ветвлении:
`sizeof(Square) = Parallelogram + Rhombus::y + Parallelogram + Rectangle::z + Square::t`.
Обращение к `x` неоднозначно — какой из двух экземпляров? Это **Diamond problem**
(проблема ромба): поэтому множественное наследование считается плохим стилем проектирования.

</details>

### 19. Какие обращения в ромбе работают, а какие нет? (`s.Rhombus::x;`, `s.Rectangle::x;`, `s.Parallelogram::x;`)

<details><summary>Ответ</summary>

- `s.x;` — ошибка (неоднозначно).
- `s.Rhombus::x;` — OK, `s.Rectangle::x;` — OK (квалификатор снимает неоднозначность **ветви**).
- `s.Parallelogram::x;` — **опять ошибка**: базовых экземпляров два, квалификатор по типу не помогает.

</details>

### 20. Если база достижима двумя путями (например, `Son : Mom, Granny`, а `Mom : Granny`) — что делает компилятор?

<details><summary>Ответ</summary>

Создаёт **два экземпляра** (по одному на путь), код скомпилируется **с предупреждением** о
дублировании, а `s.x;` и `s.Granny::x;` — неоднозначны. Каждый путь несёт **свою** копию `Granny`.

</details>

## Виртуальное наследование

### 21. Что такое **виртуальное наследование**? С чем его НЕ путать?

<details><summary>Ответ</summary>

Способ сказать компилятору: «если база достижима несколькими путями — создай **один** экземпляр,
а не по одному на путь». **Не** имеет отношения к виртуальным функциям (полиморфизму) —
совпадение терминов случайное.

</details>

### 22. Как пишется виртуальное наследование?

<details><summary>Ответ</summary>

```cpp
struct Rectangle : virtual public Parallelogram { };
// эквивалентно
struct Rectangle : virtual Parallelogram { };
```

</details>

### 23. `Rhombus : virtual Parallelogram`, `Rectangle : virtual Parallelogram`, `Square : Rhombus, Rectangle`. Сколько `Parallelogram` в `Square`?

<details><summary>Ответ</summary>

**Один.** Оба пути виртуальные — компилятор обязан создать один общий экземпляр.
Правило: **все виртуальные** пути объединяются в один экземпляр; **все невиртуальные** — свою копию.

</details>

### 24. Один путь виртуальный, другой — нет. Сколько экземпляров базы?

<details><summary>Ответ</summary>

**Два**: один общий (виртуальный) + одна «своя» копия по невиртуальному пути. Виртуальные пути
между собой объединяются, невиртуальные — никогда.

</details>

### 25. Пример из стандарта: `V` достигается одним виртуальным путём, `W` — двумя (один невиртуальный). Почему `d.x;` OK, а `d.y;` — ошибка?

<details><summary>Ответ</summary>

`x` (из `V`) виден однозначно — `V` достигнута по **одному** пути. `y` (из `W`) неоднозначен:
два пути, один из них **невиртуальный**, а невиртуальные пути не объединяются →
два экземпляра `W`.

</details>

### 26. В чём «цена» множественного виртуального наследования на практике?

<details><summary>Ответ</summary>

В памяти хранится **граф** наследования (не цепочка): сложнее выравнивание, смещения, `static_cast`;
компилятор дольше строит структуру объекта. Поэтому на практике его не любят.

</details>

## Приведение типов и срезка

### 27. Что делает `b = d;` (`Base b`, `Derived d`)? А `d = b;`?

<details><summary>Ответ</summary>

`b = d;` — **срезка из копирования (slicing)**: копируется только базовая часть, производная
теряется. Компилируется, но почти всегда признак ошибки в замысле.
`d = b;` — **ошибка**: базовый объект нельзя «раздуть» до производного.

</details>

### 28. `Base& b = d;` — что видно через `b`? Как добраться до производной части?

<details><summary>Ответ</summary>

Только часть `d`, относящаяся к `Base` (`b.a;` OK, `b.b;` — ошибка). До производной части:
`static_cast<Derived&>(b)`, но **рекомендуется** `dynamic_cast` — он проверяет тип в рантайме
(для ссылок бросает `std::bad_cast`, для указателей возвращает `nullptr`):
`auto p = dynamic_cast<Derived*>(&b);`

</details>

### 29. Чем `static_cast` отличается от `dynamic_cast`?

<details><summary>Ответ</summary>

`static_cast` — «верю на слово»: быстро, решение на этапе **компиляции**, реальный тип не проверяет
(ошибся — UB). `dynamic_cast` — «проверяю»: решение на этапе **выполнения** (runtime), медленнее.

</details>

### 30. `Base* b = d;` — что это и в каком направлении нужно кастовать?

<details><summary>Ответ</summary>

Неявное преобразование `Derived* → Base*` при `public`-наследовании (OK). Обратное (`Base* → Derived*`)
— только через `static_cast` / `dynamic_cast`.

</details>
