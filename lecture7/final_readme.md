## 2. Поиск имён при наследовании

### 2а. Сокрытие имён (hiding)

Если в производном классе объявлен метод с **тем же именем**, но **другой сигнатурой**, то одноимённые методы базового класса **прячутся** (hiding). Вызов `d.f()` при отсутствии подходящей перегрузки в `Derived` — **ошибка компиляции**.

```cpp
class Base {
    void f();          // Base::f()
};

class Derived : public Base {
    void f(int x);     // Derived::f(int)
};

Derived d;
d.f();   // ошибка: Base::f() скрыта, а f(int) без аргумента не подходит
```

Правило: как только в `Derived` появляется имя `f`, компилятор **не ищет** `f` в `Base` — перегрузка между уровнями иерархии «не работает» автоматически.

### 2б. Явный вызов имени предка

Доступ к скрытому методу предка возможен через **явный квалификатор**:

```cpp
class Base {
    int b;
    void f();
};

class Derived : public Base {
    int d;
    void f(int x);
};

Derived d;
d.Base::f(5);   // явно — обращение к версии в Base
```

Однако если наследование **приватное**, то даже `d.Base::f(5)` будет ошибкой — у внешнего кода **нет прав** обращаться к родителю.

Возможные сообщения об ошибке:

- «не видна область» (имя не найдено);
- «недоступно» (inaccessible) — имя найдено, но права доступа запрещают вызов.

Альтернатива явному квалифицированному вызову — **директива `using`** в теле класса:

```cpp
class Derived : public Base {
    using Base::f;    // подтянуть ВСЕ перегрузки f из Base
    int d;
    void f(int x);
};

Derived d;
d.f();      // теперь OK — базовые перегрузки снова видны
d.f(5);     // и свои тоже
```

`using Base::f;` восстанавливает видимые перегрузки предка и позволяет нормальной перегрузке «между классами» работать.

### 2в. Каверзный вопрос на собеседование

> Если в спецификации наследования **не написать** `public` / `private` / `protected`, что будет?

Ответ зависит от того, `struct` или `class` используется:

```cpp
// для struct: по умолчанию public (как и для полей)
struct Derived : Base { };

// для class: по умолчанию private (как и для полей)
class Derived : Base { };
```

Порядок анализа выражения: **сначала поиск имени, потом проверка доступа**. Это ключевое отличие от интуитивной «сначала права» логики.

```cpp
struct Base {
    void f() {}
};

struct Derived : Base {
    private:
        void f(int) {}
};

Derived d;
d.f();   // ошибка компиляции
```

Почему ошибка, хотя `Base::f()` публичная?

1. Компилятор сначала **решил проблему поиска**: кандидатов с подходящей сигнатурой для `d.f()` нет (в `Derived` — только `f(int)`, `Base::f()` скрыт hiding'ом).
2. Поскольку поиск имени уже не привёл к единственному кандидату, дальнейшая проверка доступа не требуется — но в данном конкретном примере ошибка возникает именно на шаге поиска, не на шаге доступа.

> **Важное правило**: компилятор сначала решает, какие кандидаты подходят по сигнатуре, и **потом** проверяет права доступа.

### 2г. Двухуровневое наследование

Классическая цепочка «бабушка → мама → сын» с приватным наследованием:

```cpp
struct Granny {
    int a;
};

struct Mom : private Granny {
    int b;
};

struct Son : public Mom {
    int c;
};

Son s;
s.c;             // OK
s.b;             // OK — public-наследование Mom → Son
s.a;             // ОШИБКА — Granny для Son «скрыта» Mom
s.Mom::b;        // OK — явный квалификатор на видимый уровень
s.Mom::Granny::a;// ОШИБКА — Mom не имеет права «выдавать» Granny
s.Granny::a;     // ОШИБКА — имя Granny не видно в Son
```

Запрет распространяется на **сам тип** предка, а не только на его поля:

```cpp
struct Son : public Mom {
    int c;

    void f() {
        Mom m;       // OK — Mom публично наследуется
        Granny g;    // ОШИБКА — внутри Son имя Granny не видно
    }
};
```

То же самое для аргументов функции:

```cpp
struct Son : public Mom {
    int c;

    void f(Granny g)     { Mom m; }  // ОШИБКА — тип Granny не виден
    void f(Granny& g)    { Mom m; }  // ОШИБКА
    void f(Granny* g)    { Mom m; }  // ОШИБКА
};
```

После «входа в `s`» слово `Granny` — **запретное**: имя недоступно из-за приватного наследования в `Mom`.

**Как обойти?** Искать имя в **глобальной** области видимости с помощью `::`:

```cpp
struct Son : public Mom {
    int c;

    void f(::Granny& g) {   // явный уход в глобальную область
        Mom m;
    }
};
```

Просто «написать имя в глобальной области» не сработает — `Granny` в глобальной области **не видно** из тела `Son` (видимость идёт через цепочку наследования, а не через глобальный «фолбэк» внутри тела класса). Нужен именно `::Granny`.

#### `friend` не «перекрывает» запрет предка

```cpp
struct Granny {
    int a;
    friend class Son;
};

struct Mom : private Granny {
    int b;
};

struct Son : public Mom {
    int c;
};
```

`friend class Son;` в `Granny` **не поможет**: запрет на `s.Granny::...` наложен **`Mom`** (приватным наследованием), а не `Granny`. Дружба с бабушкой не снимает запрет мамы.

Если же **`Mom`** делает `friend class Son;`, то запрет снят:

```cpp
struct Granny {
    int a;
    friend class Son;
};

struct Mom : private Granny {
    int b;
    friend class Son;   // мама разрешает Son общаться с бабушкой
};

struct Son : public Mom {
    int c;

    void f(::Granny& g) { Mom m; }   // теперь можно
};
```

> Дружба накладывается на **связь** между классами. Если `Son` — друг `Mom`, и `Mom` — друг `Granny` (или имеет к ней доступ), то `Son` «проходит» через маму к бабушке.

### 2д. Друзья и транзитивность

Другу класса доступно **всё то, что доступно самому классу** — но дружба **не транзитивна**.

```cpp
struct Granny {
    protected:
        int a;
};

struct Mom : public Granny {
    int b;
    friend void f();   // f() — друг Mom
};

struct Son : public Mom {
    int c;
};

// в глобальной области
void f() {
    Mom m;
    m.a;   // OK — f() друг Mom, у Mom есть доступ к a (protected у Granny)
}
```

`f()` получает доступ к `m.a` **через дружбу с `Mom`**. Но это не значит, что `f()` — друг `Granny`: если бы `a` было приватным у `Granny`, доступ был бы запрещён.

> **Дружба не транзитивна**: если `Mom` дружит с `g()`, а `g()` дружит с `h()`, то `Mom` не имеет прав, которыми обладает `h()`. Каждый уровень дружбы — отдельное соглашение.

## 3. Порядок вызова конструкторов и деструкторов при наследовании

### 3а. Как устроен «размер» производного класса

Производный класс — это **объект базового класса + дописанные поля**. Память выстраивается так:

```
| базовая часть (Granny) | производная часть (Mom) |
```

```cpp
struct Granny {
    int a;
    Granny(int a) : a(a) {}
};

struct Mom : public Granny {
    int b;
    Mom(int b) : b(b) {}   // ОШИБКА — не инициализирован Granny
};
```

Размер: `sizeof(Mom) = 8` — два `int` (4 + 4 на 64-битной, если нет выравнивания-сюрпризов).

Почему ошибка в конструкторе `Mom(int b)`? Потому что `Granny` **не имеет конструктора по умолчанию** — он определён только как `Granny(int)`. При конструировании `Mom` компилятор обязан сконструировать базовую часть, но не может выбрать ни одного подходящего конструктора `Granny` без аргументов.

> Если бы в `Granny` конструктора с аргументами **не было**, то компилятор сам сгенерировал бы конструктор по умолчанию — и код скомпилировался бы.

### 3б. Как правильно инициализировать базовую часть

Базовую часть инициализируют в **инициализаторном списке** конструктора:

```cpp
struct Mom : public Granny {
    int b;
    Mom(int b) : Granny(0), b(b) {}    // Granny(0) — явная инициализация базы
};
```

**Что нельзя**: инициализировать в списке поля **предка** как будто они свои:

```cpp
struct Mom : public Granny {
    int b;
    // Mom(int a, int b) : a(a), b(b) {}   // ОШИБКА — a не своё поле
    // Можно только инициализировать свои поля + явно вызвать конструктор базы
};
```

> Можно инициализировать в списке **только свои поля** и **явно вызывать конструктор базового класса** через его имя.

### 3в. Прямые предки — только прямые

В цепочке «бабушка → мама → сын» сын **не может** инициализировать бабушку напрямую:

```cpp
struct Mom : public Granny {
    int b;
    Mom(int b) : Granny(0), b(0) {}
};

struct Son : public Mom {
    int c;

    // Son(int c) : Granny(0), c(c) {}   // ОШИБКА
    // "Granny is not a direct base of Son"
    // — инициализировать можно ТОЛЬКО прямых предков
};
```

Сын управляет только **своим** прямым предком (`Mom`). Как инициализировать бабушку — вопрос к конструкторам `Mom`.

### 3г. Порядок вызова

- **Конструкторы**: сначала базовый, потом производный (бабушка → мама → сын).
- **Деструкторы**: в **обратном** порядке (сын → мама → бабушка).

> Это «стек»: конструкторы идут снизу вверх по иерархии, деструкторы — сверху вниз.

## 4. Множественное наследование (multiple inheritance)

### 4а. Пример: параллелограмм → прямоугольник и ромб → квадрат

```
        Параллелограмм
           /      \
      Ромб        Прямоугольник
           \      /
           Квадрат
```

```cpp
struct Parallelogram {
    int x;
};

struct Rhombus : Parallelogram {
    int y;
};

struct Rectangle : Parallelogram {
    int z;
};

struct Square : Rhombus, Rectangle {
    int t;
};
```

**Размер** `Square`:

```
sizeof(Square) = (Parallelogram) + (Rhombus::y) + (Parallelogram) + (Rectangle::z) + (Square::t)
```

То есть `Parallelogram` **дублируется** — по одному экземпляру в каждом ветвлении.

Проблема обращения:

```cpp
Square s;
s.x;                      // ОШИБКА — неоднозначно: какой x?
s.Rhombus::x;             // OK
s.Rectangle::x;           // OK
s.Parallelogram::x;       // ОШИБКА — и их два, квалификатор не помогает
```

Аналогично для функций с одинаковыми именами.

Это называется **Diamond problem** («проблема ромба»). Из-за неё множественное наследование считается **не лучшим** стилем проектирования:

> Разговоры в Яндексе: «может, разрешим множественное наследование?» — «Ага, сначала разрешим множественное наследование, потом `goto`, а потом становимся фашистами».

### 4б. Множественное наследование с разными доступами

```cpp
struct Rectangle : private Parallelogram { };
struct Rhombus   : public  Parallelogram { };

struct Square : public Rhombus, Rectangle {
    int x;
};

Square s;
s.x;   // что будет?
```

Здесь `x` из `Square` **виден** напрямую (он свой), а `Parallelogram::x` — неоднозначен (два экземпляра), но при этом один из путей **приватный** (через `Rectangle`).

### 4в. «Бабушка дважды» — предупреждение

Если база встречается в иерархии **двумя разными путями**, компилятор создаёт **два экземпляра**:

```
  Granny
    ^
    |
  Mom
    ^
    |
    Son --------
          (и напрямую)
          Granny
```

```cpp
struct Granny { int x; };
struct Mom : public Granny { };
struct Son : public Mom, public Granny { };

Son s;
s.x;   // ОШИБКА — неоднозначность (двух x)
s.Granny::x;   // тоже неоднозначно — их две
```

Код **скомпилируется**, но с **предупреждением** о дублировании. Фактическая структура памяти:

```
  Granny (от Mom)     Granny (напрямую от Son)
        ^                       ^
        |                       |
       Mom                     |
        ^                       |
        Son --------------------
```

Каждый путь наследования несёт **свою** копию `Granny`.

## 5. Виртуальное наследование ≠ виртуальные функции

**Виртуальное наследование** — способ сказать компилятору: «если базовый класс достижим несколькими путями, создай **один** экземпляр, а не по одному на каждый путь».

Это **не** имеет отношения к виртуальным функциям (полиморфизму) — термины совпадают случайно.

### 5а. Синтаксис

```cpp
struct Rectangle : virtual public Parallelogram { };
// эквивалентно:
struct Rectangle : virtual Parallelogram { };
```

`public` / `private` / `protected` по умолчанию — как и в обычном наследовании.

### 5б. Когда копию **не** делают

```cpp
struct Rectangle : virtual Parallelogram { };
struct Rhombus   : virtual Parallelogram { };

struct Square : Rhombus, Rectangle { int t; };
```

Компилятор **обязан** создать **один** `Parallelogram` — всякий раз, когда дальше по иерархии встречается виртуальная база, он следит, чтобы экземпляров не дублировалось.

### 5в. Смешанное виртуальное/невиртуальное

```cpp
struct Rectangle : virtual Parallelogram { };
struct Rhombus   : Parallelogram { };   // не виртуальный

struct Square : Rhombus, Rectangle { int t; };
```

Результат: **два** экземпляра `Parallelogram` — один виртуальный (общий), второй — «своя» копия от `Rhombus`.

> Правило: **все виртуальные** пути объединяются в один экземпляр; **все невиртуальные** создают свою копию.

### 5г. Пример из стандарта (глава 10)

Классы `W`, `V`, `A`, `B`, `D` — типовая «двойная бабушка» со смешанными видами:

```
  W (int y)            V (int x)            W (int y)
    ^                    ^                     ^
    | (невиртуальный)    | (виртуальный)      | (виртуальный)
    |                    |                     |
  A  -------------------(невиртуальный)------> B
    ^                                            ^
    |                                            |
  D  -------------------------------------------(невиртуальный)
```

```cpp
D d;
d.x;   // OK  — V достигается только по одному (виртуальному) пути
d.y;   // ОШИБКА — W достижим по двум путям, один невиртуальный → неоднозначность
```

`x` виден однозначно, `y` — нет, потому что невиртуальные пути **не объединяются**.

> Пример взят из **главы 10** стандарта C++.

## 6. Приведение типов между наследниками

### 6а. Срезка из копирования (slicing)

```cpp
Base b;
Derived d;
b = d;   // компилируется, но НЕ ЖЕЛАТЕЛЬНО
d = b;   // ОШИБКА
```

`b = d;` — **срезка из копирования**: из `d` в `b` копируется только «базовая» часть, производная часть **теряется**. Это не ошибка, но почти всегда — признак ошибки в замысле.

`d = b;` — нельзя: базовый объект не может быть «раздут» до производного.

### 6б. Ссылки и указатели

```cpp
Base& b = d;   // OK — ссылка на базовую часть d
```

Через `b` можно обращаться **только** к части `d`, которая относится к `Base`. Но как добраться до производной части?

```cpp
static_cast<Derived&>(b);   // да, можно
```

Но **рекомендуется** `dynamic_cast<Derived&>(b)` — он проверяет тип **во время выполнения** и бросает `std::bad_cast` (или возвращает `nullptr` для указателей), если преобразование невозможно:

```cpp
auto p = dynamic_cast<Derived*>(&b);   // nullptr, если b на самом деле не Derived
```

> `static_cast` — быстро и «верю на слово», `dynamic_cast` — медленно и «проверяю».

### 6в. Указатель

```cpp
Base* b = d;   // OK — неявное преобразование Derived* → Base* (при public-наследовании)
```

Обратное преобразование (`Base*` → `Derived*`) — только через `static_cast` / `dynamic_cast`.

### 6г. Виртуальное наследование и его «цена»

- Множественное виртуальное наследование **не очень любят** на практике;
- Компилятор **долго** строит структуру объекта;
- В памяти хранится **граф** наследования (а не просто цепочка) — из-за этого и возникают сложности с выравниванием, смещениями и `static_cast`.

## Короткая шпаргалка

| Тема | Главное |
|---|---|
| **Hiding** | Одинаковое имя в `Derived` **прячет** все одноимённые методы `Base` (с любой сигнатурой) |
| **Явный вызов** | `d.Base::f(5);` — работает только при `public`-наследовании |
| **`using Base::f;`** | Подтягивает все базовые перегрузки в область видимости `Derived` |
| **Порядок анализа** | Сначала **поиск имени**, потом **проверка доступа** |
| **`struct` vs `class`** | Без спецификатора: `struct` → `public`, `class` → `private` |
| **Дружба** | Не транзитивна; снимает запрет **того**, кто сделал `friend` |
| **Конструкторы** | База → производный; **только прямые** предки в инициализаторном списке |
| **Деструкторы** | Обратный порядок конструкторов |
| **Множественное наследование** | **Diamond problem**: дублирование баз → неоднозначность имен |
| **Виртуальное наследование** | Один экземпляр виртуальной базы на всю иерархию (≠ виртуальные функции!) |
| **Срезка (slicing)** | `b = d;` — потеря производной части; использовать **ссылки/указатели** |
| **`static_cast` / `dynamic_cast`** | Первый — «верю», второй — **проверяет в рантайме** (рекомендуется) |
